## 一句话

把性能硬门槛 H1 的判据从「行」改成「**字节**」（`bytesRead.max ≤ 6,144,000 B`），并把「候选读取量」拆成**四个并列读数**落盘；旧行数判据**降级为并列观测**（不再判红绿，常量保留不删）。

## 为什么必须改

「行」是**实现相关的单位**（768 B 的码 / 96 B 的码 / 打包块 ⇒ 同一个「行数」含义完全不同）⇒ 换存储形态就换了一把尺。且 C′ 档的候选宇宙 ≈ 5,521 行**必然 > 2,000** ⇒ 留着当判据 ⇒ 本档永远红、无法交付 ⇒ 降级是**必需**，不是偏好。

字节口径 = 2,000 行 × 3,072 B，**与旧 H1 同源** ⇒ 可比；只计向量载荷 ⇒ 是真实搬运量的**下界** ⇒ **判据偏严、不会假绿**。

## 判据三件套

| 标签 | 判据量 | 门槛 |
|---|---|---|
| `（H1′）` | `writeSegments.vectorByteReads.bytesRead.max`（判定取 `max`） | ≤ **6,144,000 B** |
| `（H2′）` | `bytesRead.max ÷ (库规模 × 3,072 B)`（同义规模无关写法 ⇒ 必然同时红/同时绿） | ≤ **0.2%** |
| `（PRUNE_RATE）` | `embeddingCalls ÷ candidateUniverse`（分子 = `get()` **调用次数** ≡ `prune` 的 `exactReads`） | ≤ **15%** |

旧 `（H1）`/`（H2）` **判红信息里一个都不许再出现**（断言 5 两头锁死）。

## 计时口径（关键，决定基线要不要重采）

- **写路径 = 两轮制**：轮 A 计时**不装**计数器 / 轮 B 计量**装**计数器 · 同一份输入 ⇒ **逐字复现 HEAD 取时位置** ⇒ `vectorCandidateScan` 与历史基线**逐位可比** ⇒ **百万级基线不用重采**。
- **读路径 = 单轮**：计数器装着且在计数 ⇒ 与 HEAD **逐字同形** ⇒ 历史基线口径**没动**。

## 落盘结构

四读数用 **ADR §8.5 的原名**（`memoryRowsRead` / `codeRowsRead` / `bytesRead` / `candidateUniverse`），形态 = `CountSummary` 分布；`breakdown` **13 项**（第 13 项 = `embeddingExactRows` = `scoreOf` 返回行数）。
两个容器：`writeSegments.vectorByteReads`（判据量）＋ 顶层 `vectorRouteByteReads`（观测值）。
**旧落盘键零删除、零改名**（HEAD 键名集合差集 `DELETED` = 空）。

## 字节计量装置

`bench/lib/byteSources.ts`：**形状登记制**（7 个登记形状，键 = 归一化 FROM/JOIN 表集合 + 归一化 SELECT 源列名集合）。**未登记语句 ⇒ 命中零来源 ⇒ `unclassifiedRows` ⇒ 判红**（口径不完整）。字节**当场累加标量** ⇒ O(1) 内存。

## 本轮抓到的真问题（三处都是「恒绿守卫」那一类）

1. **读路径 `samplesAligned` 曾是恒真的** —— `readByteSamples.length === vectorRouteSamples.length`，两个 `push` 在同一循环体内 ⇒ 长度必然相等 ⇒ 它挂在判红守卫上却**永远打不红** ⇒ 换成「逐样本 实测桶成员行 === `route()` 侧推算桶成员行」（**实测 20/20 逐位相等**）+ 纯函数导出 + 负控（正控 + 4 种负控）。
2. **`bench/perf.ts` 里「同一件事说多遍、其中一遍是错的」又栽了一次** ⇒ 已修 + 新增「**注释不许说谎**」机器守卫（扫描源码文本 ⇒ 短语所在行的 ±3 行窗口内必须出现否定标记）。
3. **两份 mermaid 副本曾各自演化**（接口名对不上实现 + 写着旧单轮语义）⇒ 改成「② §12 的**逐字抽取**」+ 新增 `scripts/check-mermaid-copies.ts`（**锚点定位 + 结构体检 + 自带 10 个负控**）。

### ★★ 本轮挖到的**根本性发现**（它改变了排序，也改了口径）

**schema 事实**（三处一致）：
```sql
CREATE UNIQUE INDEX idx_vcm_memory_unique ON vector_cell_members(memory_id);
-- ★ 一条记忆只属一个细桶（最终防线）
```
⇒ ⇒ **同批桶内 `COUNT(DISTINCT memory_id)` 恒等于 `COUNT(*)`** ⇒ ⇒ 三件事连锁倒下：

| 原来的说法 | 真相 |
|---|---|
| ① `:199`「一个 memory 落在多个命中桶时 `COUNT(DISTINCT)` 会小于成员行总数 ⇒ 1M 下不成立」 | ★ **前提被 schema 推翻** ⇒ ⇒ **禁令保留、理由换成「两个量来源不同」** |
| ① `:202`「一个记忆只属于一个细桶 ⇒ 桶间不重复 ⇒ 两者必然相等」 | ★ **对** ⇒ ⇒ 它成了「写路径 = 同源 ⇒ 必然相等」的根据 |
| QA-1「登记 3」断言「这两个量**确实不是同一个东西**」（941 == 941） | ★ **前提错** ⇒ ⇒ **不是「等 1M 档验」，是「换守卫形态」** |

⇒ ★★ **更狠的推论**：既然 `candidateUniverse` 与 `bucketMemberRows` 在同批桶内**数值恒等** ⇒ ⇒
**「接线被换成 `candidateUniverse`」这个变异在数值上【完全不可见】** ⇒ ⇒
★ **守卫必须能看见「接线喂了哪个字段」** ⇒ ⇒ **逼出了「把接线抽成纯函数」这个动作** —— 否则登记 2/3 **永远写不出来**。

⇒ ★★★ **QA 挖出的第三条（登记 3 的「可验证形态」）**：禁令在**【接线层】成立、在【判定层】不成立** ⇒ ⇒
⇒ **「同一列 ⇒ 不成立」这种判定是恒假的** ⇒ ⇒ **口径必须写明「这条禁令只在接线层按来源验」** ⇒ ⇒ 否则下一个人会照直觉写出恒假断言（QA-1 那条就是这么来的）。

### ★ T07 写脚本前先看的四条预警
1. ❌ **不许用 `bucketMemberRows === candidateUniverse`** ⇒ `candidateUniverse` 是 `COUNT(DISTINCT memory_id)` ⇒ 一个记忆落在多个命中桶时**小于**成员行总数 ⇒ ⇒ 1M 不成立 ⇒ ⇒ **假绿**。⇒ **正确判据 = 逐样本 `bucketMemberRows === bucketMemberRowsDerived`**（与规模无关）。
2. ⚠️ **软删不破坏那个相等**（工程师的预警偏保守 ⇒ QA 核过两条 SQL）⇒ `ivf.ts:517` 与 `bucketAssign.ts:301` **都不带 `deleted` 过滤 ⇒ 对称** ⇒ ⇒ 该相等是**结构性的** ⇒ ⇒ 只在「命中桶不同」时才不等 —— **那正是它要抓的**。
3. ℹ️ **ADR §8.6 的 4.44 MB 是下界** ⇒ 1M 实测 > 它属**预期**，**别当失败条件**；**当前口径的预期值是 4,262,144 B 那条**。
4. ⚠️ **PRUNE_RATE 分母 = `candidateUniverse`**（不是 `bucketMemberRows`）⇒ ⇒ 且**分子必须是 `embeddingCalls`**（调用次数 ⇒ 返回 `undefined` 也计）⇒ ⇒ 用「返回行数」= 偏松 = **假绿**。
