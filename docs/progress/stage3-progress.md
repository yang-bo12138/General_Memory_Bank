### 2.1 裁决一：那两条硬门槛（向量路 P99 ≤ 20ms、占比 ≤ 20%）**不再成立 ⇒ 重新定档**

**结论**：**这两条不再是硬门槛。** 新的硬门槛是 **H1：向量路单次查询的候选读取行数 ≤ 2,000 行**
（＋ **H2**：同义的比例写法 **≤ 0.2%**）。向量路的**绝对毫秒**降为**按存储介质分档的参考线（R1）**；
「向量路占总耗时」降为**参考线（R2）且口径待重定义**。

**为什么必须重裁（触发原因）**：早前裁决（2026-11-01）的依据是
「`recall()` 的**向量路整路缺席**（`routes.vector.ran` 恒 `false`）⇒ **向量路的耗时一条都没进 recall 的 P99**」。
⇒ ⚠️ **那个前提只在「库没训练过」时成立**。
⇒ 库一旦**训练完整跑完**（`memories` = 桶归属 = **1,000,000** / 细桶 **9,966**），
**向量路就真的跑了**（实测 p50 **89.59ms** / p99 **229.66ms** / 占比 **83.57%**）
⇒ ⇒ **那两条硬门槛第一次拿到了真实数据，而且是「不达标」**
⇒ ⇒ ⇒ **必须重新裁决**（⚠️ 注意：是**前提失效**，不是**结论被推翻**）。

**为什么新判据必须与存储介质解耦（三条理由 · 逐条可核）**：

| # | 理由 | 证据 |
|---|---|---|
| ① **归因错误（主因）** | 向量路成本 ≈ `候选行数 × 每行读成本` ⇒ **主体是「读多少行」**；「每行读多快」由**介质 + 页缓存**决定 ⇒ **把毫秒写死 = 把「这台机器的磁盘有多快」当成「分桶架构好不好」** | ⚠️ **实测（架构师独立测量 · 2026-11-02 · 不依赖百万级库）**：`dot()`（`src/vector/dot.ts`）对 **5,900 × 768 维**做全量点积 = **5.19ms**（p50，7 轮）⇒ **§4.15.3 的「≈ 3~5ms」估算其实是准的——但它只是「计算下界」，没算「把那 5,900 行 3KB 的 `embedding` 读出来」** ⇒ ⚠️（推断）实测 p50 89.59ms 里 **≈ 84ms 是行读开销** ⇒ ⇒ **「优化点积」救不了这条门槛；能救它的只有「少读行」**（或「每行更小」——那是阶段 1 的 schema 决策，P2 改不动） |
| ② **可兑现性** | **硬门槛必须能被「被考核方」兑现**（早前裁决自己的方法论，继续适用）⇒「20ms 绝对值」在**本机**等价于「候选行数 ≤ ~1,400~2,500 行」（⚠️ 推断，按实测每行读成本 8~14µs 折算）⇒ 它把**两件 P2 改不动的事**（**随机读的成本** 与 **`memories.embedding` 的行宽**）写进了硬门槛 ⇒ ⇒ **恒红且与分桶无关** ⇒ 按早前裁决自己的标准，它**不是硬门槛** | 见 ① 的每行读成本折算 |
| ③ **区分度** | **机械盘是本机的属性，不是架构的属性** ⇒ 同一份代码、同一个分桶，在 SSD 上「过」、在 SATA HDD 上「不过」⇒ **判据测的是介质不是架构** ⇒ **绝对毫秒门槛必须与介质解耦** | 实测机器 = `D:` = SATA 机械盘（~1.75 MB/s 随机读口径），库本体 4.5 GB ≫ 可用内存 |

**新门槛的完整定义**：

| # | 指标 | 门槛 | 类型 | 量的是谁的成本 | 为什么这样定 |
|---|---|---|---|---|---|
| **H1** | **向量路单次查询的候选读取行数** | **≤ 2,000 行** | **硬门槛**（归 P2） | **P2**：探针数 × 桶粒度 | **纯计数 ⇒ 与介质无关**；**2,000 是 P2 自己在写入路径上已经写死的数**（§4.9 步骤 3a2「候选 ≤ 2000」＋ P2-T07 的硬断言）⇒ **同一个库、同一个量、同一个被考核方** ⇒ **可兑现** |
| **H2** | **候选读取行数 ÷ 库规模** | **≤ 0.2%** | **硬门槛**（归 P2；H1 的规模无关写法） | 同上 | 1M ⇒ ≤ 2,000 行；10M ⇒ ≤ 20,000 行 |
| **R1** | **向量路 P99（绝对毫秒）** | **按介质分档记录** | **参考线**（记实测值 + 归因，不判 P2） | **介质 × 每行读成本**（P2 改不动） | **介质解耦的落点**：毫秒数**降级为观测值**，判据由 H1/H2 承担 |
| **R2** | **向量路占总耗时** | **暂不可判定**（口径待阶段 4 接线后重定义） | **参考线**（只记录） | — | ⚠️ **口径缺陷**：现在的 83.57% = `向量路均耗时 ÷ (recall 均耗时 + 向量路均耗时)`（`bench/perf.ts:263`）⇒ **recall 那一侧根本没走向量路** ⇒ **它是「接线后」的假设值，不是流水线内的实测占比** |
| **R3** | **recall P99（含向量路）** | **≤ 200ms** | **参考线**（**接线后的真口径**） | 文本路 + 图谱路 + 向量路 | **H1 是它的前置** |
| **R4** | **recall P99（不含向量路 · 现状口径）** | **≤ 200ms** | **参考线**（归文本路 + 图谱路） | 文本路 + 图谱路（P2 未改） | 实测 108.99ms ⇒ **达标** |
| **R5** | **写入 P99** | **≤ 5ms** | **参考线** | 写入路径的索引维护 **＋ 写入路径的向量候选扫描（P2 的代码）** | ⇒ 「纯归文本路」**已不准确** |

**「占比 ≤ 20%」为什么取消为硬门槛（可算的论证）**：
「占比 ≤ 20%」在本库上等价于「**向量路 ≤ 4.6ms**」
（分母侧的文本路 + 图谱路均耗时实测 **18.57ms** ⇒ `v/(18.57+v) ≤ 0.2` ⇒ `v ≤ 4.64ms`）
⇒ 而 **4.64ms < 实测的纯计算下界 5.19ms** ⇒ **在「候选 5,900 行」这个前提下它不可达**
⇒ ⇒ 它要么要求「候选行数再降一个量级」（⇒ 与「吻合率 ≥ 0.98」直接冲突，见下），
⇒ 要么它测的就不是「分桶架构」而是「文本路有多快」⇒ ⇒ **降为参考线**。

**⚠️ ★ H1 与「吻合率 ≥ 0.98」的张力（必须一起写下来，否则会被当成矛盾）**：
候选行数从 5,900 降到 2,000 只有两条路：
**(a) 探针数 50 → ~17**（探测比例 0.5% → 0.17%）或
**(b) 桶粒度变细**（`ROUTER_FINE_CENTERS` 10,000 → ~30,000 ⇒ 每桶 ~33 行 ⇒ 50 桶读 1,650 行，探测比例同样降到 0.167%）
⇒ **两条路的「探测比例」都下降 ⇒ 吻合率会掉**（⚠️ 推断）
⇒ ⇒ **H1 达标** 与 **吻合率 ≥ 0.98** 必须**同时成立**；
⇒ ⇒ 若冲突，**结论是「桶粒度不够细」**（**不是**「H1 可以放松」）
⇒ ⇒ ⚠️ **而桶粒度变细会撞上 §三 的缺陷 ②**（细层分组 200 倍重复扫描 ⇒ 建中心段 ~98 分钟）
⇒ ⇒ **H1 的兑现路径必须由工程师在「训练成本」与「读放大」之间给出方案，并同时解决那条缺陷**。

**⚠️ ★ 换算关系（介质解耦的可操作部分，必须写进 bench 报告）**：
`向量路耗时 ≈ 候选行数 × 每行读成本`（本机实测每行 ≈ **8~14µs** ⇒ **2,000 行 ≈ 16~28ms**）
⇒ **同一个 H1（2,000 行），在 SATA HDD 上是 ~16~28ms、在 NVMe SSD 上是 ~2~5ms**
⇒ ⇒ **所以绝对毫秒门槛必须按介质分档记录，而判据由 H1/H2 承担**
⇒ ⇒ **bench 必须把「存储介质类别」与「每行读成本」记进落盘 JSON**
（否则换一块盘，判据的含义会静默改变——这正是「文档与数据不一致」的另一种形态）。

### 2.4 裁决四：`recluster()` 的 `skipped` 枚举 —— **扩**

**结论**：**扩成 `'too_soon' | 'disabled' | null`。**

**理由**：
1. **类型就是契约**。现定义 `skipped: 'too_soon' | null` 等于宣称「唯一的跳过原因是间隔太短」，
   而实现里**有第二个原因**（`coactivation` 关闭）⇒ **类型在撒谎** ⇒
   宿主必须**读源码注释**才知道怎么解读 ⇒ **这不是契约，是文档**。
2. **`coactivation=false` 不是边角**，它是**一等公民**（§5 的 A/B 基线开关）⇒ 宿主会**天天**撞上它。
3. **可预见**：「没重算」将来还会多出第三个原因（没有可用的共激活边 / 库为空 …）⇒
   **枚举现在就该留好位置**，否则那条「约定」迟早会失效。

**完整的新定义（已写进 `DESIGN-v2.md` §6）**：

```
recluster(now?: number): {
  clusterCount: number; largestClusterRatio: number;
  computed: boolean;          // ★ 本次**是否真的重算了**
  skipped: 'too_soon' | 'disabled' | null;
}
```

| `skipped` | `computed` | `clusterCount` / `largestClusterRatio` | 含义 | 写库 / 记事件 |
|---|---|---|---|---|
| `null` | `true` | 本次重算的结果 | 真的重算了并发布了新快照 | **是**（`action='recluster'` 事件） |
| `'too_soon'` | `false` | **上一次已发布快照**的簇数（`largestClusterRatio` = 现算的「最大块 / 未删记忆数」） | 距上次发布不足 `CLUSTER_RECALC_INTERVAL_MS` ⇒ 幂等跳过 | 否 |
| `'disabled'` | `false` | **0** / **0** | 机制开关 `coactivation` 关闭 ⇒「簇不计算也不使用」⇒ **「簇」这件事根本不存在**（不是「存在但为空」） | 否 |

- **不变式**：**`computed === (skipped === null)`** ⇒ `computed` 是**派生量**；
  保留它是为了 **§6 的向后兼容**（宿主可以只读 `computed`）。
- **判定顺序（实现必须照这个顺序）**：① **只读守卫**（§7.1）⇒ ② **机制开关 `coactivation`** ⇒ ③ **间隔闸门**
  ⇒ ⚠️ **只读守卫在开关判定之前**（§7.1 的守卫**不得随开关变化**，否则「关掉开关就绕过了只读守卫」）。
- **宿主的读法**：先看 `computed`（有没有算）→ 再看 `skipped`（为什么没算）。
  ⚠️ **不要靠 `clusterCount` 的值判断有没有重算。**

**实现侧的改动量（很小 ⇒ 值得做）**：
当前实现 `coactivation=false` 时返回 `{ computed: false, clusterCount: 0, largestClusterRatio: 0, skipped: null }`
⇒ **两个数值已经是对的**（0 / 0）⇒ **只需把 `skipped` 的取值从 `null` 改成 `'disabled'`**（＋ 类型 ＋ 注释 ＋ 断言）。

⚠️ **兼容性提示（**必须写进 §6 的破坏性变更清单**）**：
旧宿主若写成「`skipped === 'too_soon'` ⇒ 跳过，否则 ⇒ 算了」，会把 `'disabled'` 误判成「算了」
⇒ **破坏性变更**；⇒ **缓解**：§6 本来就要求「宿主必须靠 `computed` / `skipped` 区分」⇒
**只要宿主先看 `computed` 就不会踩** ⇒ ⇒ **要求**：任何改动 `recluster()` 返回类型的动作，
必须在 `docs/DELIVERY.md` 的破坏性变更清单里留一行。

### 2.5 裁决五：`clusters()` 的 `adoptedMemories` / `totalMemories` —— **确认留真值**

**结论**：**确认**。`coactivation=false` 时**簇相关**的一切全 0 / 空，
但 **`adoptedMemories` / `totalMemories` 留真值**。

**理由**：
1. §6 明写 `clusters().adoptedMemories` 与 `stats().adoptedMemories` 是
   「**同一个数、同一口径、同一实现**」⇒ **必须恒等** ⇒ 填 0 会**直接破坏那条恒等式**
   （`stats()` 报真值、`clusters()` 报 0 ⇒ 同一个量两个口径 ⇒ 这正是本仓库反复踩过的坑）。
2. 它们是**库级事实**（`access_count > 0` 的未删记忆数 / 未删记忆数），**不是簇的事实** ⇒
   **它们不读簇表** ⇒ 「簇不计算也不使用」这条约束**不受影响**。
3. 实现上两边走的是**同一个函数**（`countAdoptedMemories(db)` / `countLiveMemories(db)`）⇒ **恒等由构造保证**。

**⚠️ 补进设计稿的读法警告（已写进 `DESIGN-v2.md` §6）**：
**宿主判断「簇覆盖了多少」必须看 `coveredMemories` / `coverage`，不能看 `adoptedMemories` / `totalMemories`**
—— 后两个是库级事实，与「簇是否存在」无关。

## 三、★★ 本阶段暴露的产品级缺陷（**只登记，不修**）

> ⚠️ **本轮没有动 `src/**`** ⇒ 以下三条**只登记，不修**。
> ⚠️ **它们是在百万级重训时实测暴露的，不是 bench 的问题，是产品的运维路径缺了一环。**

### 3.1 ① `BucketRebuildOptions` **不透传 `maxIterations`**

| 项 | 内容 |
|---|---|
| **位置** | `src/vector/rebuild.ts:70-84`（`BucketRebuildOptions` 里**没有** `maxIterations`）⇒ `:180-183` 调 `buildCentroidModel` 时**只传了 2 个参数** |
| **后果** | 百万级重训**没法限制迭代次数** ⇒ **没法用「降迭代」来换内存 / 时间** ⇒ **只能被 OOM / 超时打断** |
| **归属** | **工程师**（阶段 4 排期） |

### 3.2 ② 细层分组**对每个粗桶全量扫 100 万向量**（200 倍重复扫描）

| 项 | 内容 |
|---|---|
| **位置** | `src/vector/ivf.ts:241`（`buildCentroidModel` 里，**每个粗桶都遍历一次全部向量**）⇒ 200 × 100 万 = **2 亿次内层遍历** |
| **后果** | 建中心段实测 **~98 分钟**；训练段采样峰值 **8.20 GiB** ⇒ **16 GB 机器上百万级重训必然 OOM**（实测：可用物理内存降到 **0.28 GB**、页面文件用掉 **3.37 GB**） |
| **归属** | **工程师**（阶段 4 排期）⚠️ **注意：这条与裁决一的 H1 直接相关**（H1 若靠「桶粒度变细」兑现 ⇒ 细层工作量还要涨） |

### 3.3 ③ ★ **没有「只补跑迁移段」的运维入口**

| 项 | 内容 |
|---|---|
| **现象** | 百万级重训 = 「读向量 → **建中心**（k-means）→ **迁移归属** → 清理 → 删旧桶」⇒ 实测 **建中心段 ≈ 98 分钟** ＋ **迁移段 ≈ 38 分钟** ≈ **合计 ≈ 2 小时 16 分** ⇒ **一次跑完会被环境的后台进程时限掐掉**（实测 ~2h07m 时进程被杀，停在迁移段 823k/1M；**上一位工程师那次也停在迁移段 ~97% 处 ⇒ 同一个坑**） |
| **后果** | ⇒ **那 98% 的成果就白费**（前一位工程师的库就是这样停在 989,500 / 1,000,000）⇒ ⇒ **没有自救路径** |
| **归属** | **工程师**（阶段 4 排期）⇒ **`rebuildBuckets` 应提供「跳过建中心、只重跑迁移」的入口**（**本轮是手工脚本绕过的 ⇒ 工具链没有这个能力**） |

### 3.4 ⚠️ ★ ③ 的可行解**已被实测验证**（**这一条是本节最有用的部分**）

- **「建中心」的产物在迁移之前就已落库** ⇒ 中心向量在 `vector_coarse_cells` / `vector_fine_cells` 的
  `centroid` 列 ⇒ **Float32 bit 级往返**（不丢精度）⇒ ⇒ **补跑迁移段即可**（**~38 分钟**）。
- **归属逐条相同**：同一套桶 id（索引派生 ⇒ 可复现）＋ 同一个生产 `assignBucket` ＋ 幂等的「先删后插」。
- ⇒ ⇒ **所以 ③ 是一条「加一个入口」的欠账**，**不是一条「做不到」的欠账** ⇒ **做起来是可行的**。

### 3.5 ★ 给阶段 4 的一句话

**百万级用户第一次重训就会踩到 ① + ②，且踩到之后没有自救路径（③）
⇒ 这不是 bench 的问题，是产品的运维路径缺了一环。**

### 10.3 ★★ 修正二：两条兑现路径按 **max 那一档**重算（★ 本轮最需要算准的一段）

**需要收缩多少**（**推导层**）：

- ⇒ **重算倍数 = 6.391 ÷ 2.95 = 2.166** ⇒ ★ **与「12,782 ÷ 5,900 = 2.167」互为印证**（同一个 2.17，两条独立算法路径对上）。

**候选行数 ≈ 命中桶数 × 每命中桶密度** ⇒ 两条路径：

**(a) 探针数 `ROUTER_NPROBE_FINE` 50 → ~7~8**
- 算式：`12,782 × (P ÷ 50) ≤ 2,000` ⇒ **`P ≤ 7.82`**
- ⇒ **整数取值 7（安全，推导 1,789 行）／ 8（推导 2,045 行 ⇒ 仍超门槛 2.3% ⇒ 不可单独采用）**
- ⇒ **探测比例**：50 ÷ 10,000 细桶 = **0.500%** → 7 ÷ 10,000 = **0.070%**
- ⇒ **代价：训练成本 0、常驻内存 0**（不动分桶）⇒ **最便宜**

**(b) 桶粒度变细（细桶总数 `ROUTER_FINE_CENTERS` 10,000 → ~64,000）**
- 算式：`12,782 × (10,000 ÷ F) ≤ 2,000` ⇒ **`F ≥ 63,910`**
- ⇒ **取 64,000 细桶**（= **6.391 倍**；按 200 粗桶 ⇒ **320 细桶/粗桶**，原 50 细桶/粗桶）

- ⇒ **探测比例**：50 ÷ 64,000 = **0.078%**
- ⇒ **代价（必须一起算，否则方案是错的）**：
  - **训练成本**（⚠️ **推断层**：按「∝ 细中心数」线性外推）：建中心段实测 **97.8 min** × 6.391 ≈ **625 min ≈ 10.4 h**；迁移段实测 **38.5 min** × 6.391 ≈ **246 min ≈ 4.1 h** ⇒ **合计 ≈ 14.5 h**（原实测合计 **136.3 min**）⇒ ⚠️ 线性外推是**上限**（建中心段里「读 100 万向量」那一截是固定的 ⇒ 真实值应略低）；

  - **桶成员表不涨** ✅（每条记忆仍只挂一个细桶 ⇒ `vector_cell_members` 仍是 100 万行）；
  - **反例：桶变细反而更安全** —— `ROUTER_BUCKET_MAX = 300`（桶内成员数 P95 上限，超过触发全量重训）⇒ 现口径下**最坏命中桶 255.64 行 ⇒ 已逼近 300** ⇒ 细桶化后降到 ~40 行 ⇒ **离重训线更远**（⚠️ 推断层）；

| 方案 | `ROUTER_NPROBE_FINE` | 细桶总数 | 探测比例 | **max 档候选行数** | 收缩倍数 | 训练成本 | 常驻桶中心 |

### 10.5 ★ 「冷盘档 vs 热盘档」这个新变量的含义

| 指标 | **冷盘档**（本次 · 库**不在**页缓存中） | **热盘档**（上一轮 · 库**在**页缓存中） | 冷 ÷ 热 |
|---|---|---|---|
| 向量路 P99 | **4969.50 ms** | **229.66 ms** | **≈ 21.6 倍** |
| 向量路均值 | 954.74 ms | 94.45 ms | ≈ 10.1 倍 |
| 写入 P99 | **1199.99 ms** | 644.06 ms | ≈ 1.86 倍 |
| recall P99 | **164.44 ms** | 108.99 ms | ≈ 1.51 倍 |
| 每行读成本（**推导值**） | **212.025 µs/行** | ≈ 8~14 µs/行 | ≈ 15~26 倍 |
| **H1（max）** | **12,782 行** | （该轮未采 H1/H2） | — |

★ **含义（三条）**：
① **毫秒数 = 「介质」× 「页缓存状态」× 「候选行数」三个因子的乘积** ⇒ ⇒ **同一个算法、同一个库、同一台机器，只换页缓存冷热 ⇒ 向量路 P99 差 21.6 倍**

② ⇒ ⇒ **H1 / H2 之所以能当硬门槛，是因为它们只看第三个因子（行数）** ⇒ ⇒ **「判据必须与介质解耦」这条裁决，第一次有了实测支撑**；
③ ⇒ ⇒ **反过来，它给出了一条新的纪律**：「每行读成本」**不是一个可以跨报告复用的常数** ⇒ ⇒ **任何换算必须写明档位**（见 §10.4(b)）。

### 11.6 ⚠️ 自检工具本身也会骗人 —— 变异自检方法的**加固**（2026-11-02 · 同一轮追加）

⚠️ **本节记录一个真实的自检事故**（**不是假想的**）⇒ **它推翻了 §11.4 里记的那个方法**。

⚠️ **事故**：§11.4 记录的变异自检方法是「`cp` 备份 → 改 → 跑 → `cp` 还原 → sha256 对账」
⇒ ⇒ **这个方法在本轮真的失效过一次** ⇒ **变异被留在了工作树里**
（⇒ 被 `git status` 发现 ⇒ 已用 `git checkout --` 还原
⇒ ⇒ **并用 sha256 对账确认「还原后 == 变异前」** ⇒ ⇒ **提交进版本库的内容是干净的**
（`git show HEAD:bench/perf.ts` 的 sha256 == 变异前的基线 sha256 == `23c2bd9e…`））。

⚠️ **失效的原因（两条，都很朴素）**：
· **还原是普通语句**（不在 `finally` 里）⇒ **一旦中途抛错就不会还原**；
· **Windows 上 `copyFileSync` 遇到文件占用会抛错**（vitest 的 worker 还持着那个文件时）
⇒ ⇒ **「看起来跑了、其实没还原」** ⇒ ⇒ **⇒ 门禁再绿，提交里也可能带着变异**。

⇒ ⇒ **加固后的方法**（**本轮已用它重跑 A / B 两条变异 ⇒ 均红 ⇒ 均逐位还原 ⇒ 工作树干净**）：
· **还原放在 `finally` 里** ⇒ **任何路径都会还原**；
· **还原用「读出内容 → 写回」**（不用 `copyFileSync` ⇒ 不受文件占用影响、也不改 mtime）；
· **还原后必须 sha256 对账** ⇒ 对不上 ⇒ **直接非零退出**（不许「看起来还原了」）。

⇒ ⇒ ★ **教训（与 §11.4 那条并列 ⇒ 一起进自查清单）**：
· **「一致性」≠「判别力」**（§11.4：想不出「什么变异会让它变红」⇒ 那条断言可能就是恒绿的）；
· ★★ **「验证工具自己会不会骗我」** —— **一个自己都可能失手的验证工具 ⇒ 它给的「绿」不算证据**
⇒ ⇒ **验证工具的可靠性必须与被验证对象同等对待**（**还原要 `finally` 保护 + 哈希对账**）
⇒ ⇒ **这是本仓库纪律的第三次应用**：§11.4 的「先想什么变异会让它变红」＋ 本条的「先想验证工具本身会不会失手」。

⇒ ⇒ **另有一件事已逐项核实过（免得误判成「门禁会改文件」）**：
**`pnpm run verify` 的每一环（typecheck / lint / test / 八个 check 脚本 / build）都单独跑过并逐一检查 `git status`**
⇒ ⇒ **没有任何一环会改动仓库里的任何文件** ⇒ ⇒ **工作树变脏只可能来自「手工跑变异脚本」这一步**
⇒ ⇒ **⇒ 所以「门禁绿 ⇒ 提交干净」这个链条本身是可靠的**。
