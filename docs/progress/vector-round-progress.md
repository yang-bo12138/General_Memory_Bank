## 三、★ 三条会让人读错的「口径」（本轮最贵的产出）

### 3.1 那个读数测的**就是**「接线后召回的向量扫描量」（⭐ 2026-11-03 起它叫 **R6**；**H1/H2 已归口到写入路径**）—— 它从来不是纸面数字

`bench/perf.ts` 里 H1 的取数是 `:364-365` 用**召回探针**（`ROUTER_NPROBE_COARSE=20` / `ROUTER_NPROBE_FINE=50`）构造后端，
`:457-463` 直接调 `backend.search()`（**不经过 `recall()`**），`:471` 收 `candidateRows`。
⇒ 12,782 行这个数**一直代表**「每次带向量的召回会读多少行」，只是**没有任何用户操作会触发它**。

⚠️ **绝不能说「H1 与召回路径无关」。** 唯一正确的说法是两条并行：
- 接线**不改变** H1 的读数（因为 bench 绕过 `recall()`）；
- **但该读数本来就等于接线后召回的向量扫描量** ⇒ **接线不会让 H1 变绿，只会让它第一次测到真东西**。

⚠️ ★★ **2026-11-03 归口之后，上面这段要按新主语重读一遍**（否则会与前后的表打架）：
- **12,782 行这个读数的主语是「召回路径的向量扫描量」** ⇒ 它现在是 **R6（`RECALL_VEC_ROWS`）**，
  一条**观测值**（**本轮不设门槛、不判红绿**）；
- **H1/H2 的主语是「写入去重路径」**（写入探针 8/20）⇒ 它的实测值是 **max 5,521 行 = 2.76 倍 ⇒ 红**
  （**冷盘档那一轮 · 样本 500**，本轮未复测）；
- ⇒ ⇒ **两条都还是红的**。⚠️ **「2.76 倍」不是「6.39 倍被修好了」**：**6.39 倍没有变小，它换了主语**。
  ⇒ 判读纪律：**R6 的读数不许拿去判 H1**，H1 的数不许拿去代表召回路径。
  ⇒ 正文见 `DESIGN-v2-errata.md` **§11.8 勘误 ⑫**；门槛表见 `DEVELOPMENT-PLAN.md` P2-T08。

### 3.2 时间窗与 `ARCHIVE_LINE` 在默认参数下**是同一个边界** ⇒ 它单独不可观测

`coarseGateWindow()`（`scoring.ts:783`）算窗口用的就是 `archiveSpanFactor(ARCHIVE_LINE)`，τ 取 `MAX_STABILITY × MAX_PIN_FACTOR`。
⇒ 窗口边界恰好是「任何记忆最迟衰减到归档线」那一刻 ⇒ **落在窗外的记忆，`intensity` 必然已 ≤ `ARCHIVE_LINE`**。

⇒ 推论：它是**索引友好的预筛**，不是独立的语义闸门。**后果是测试陷阱**：
把 `filter` 换成 `{}`（等于关掉时间窗）**测试仍然可能全绿**（QA 第一版就踩了）。
要测它，必须造 **over-fetch 饱和**形状：`> VECTOR_TOPK × 3 = 60` 条「窗内但已归档」的旧记忆 + 1 条「窗外但很新」的记忆
⇒ 正确实现 `candidates = 1`，绕过时间窗则 `candidates = 0`。

### 3.3 「吻合率 ≥ 0.98」是**数据 + 探针配置**的特定值，不是实现性质

一次实测（3,200 条簇状语料 · 16 簇×200 · 粗 16 / 细 64 · 6 条查询，每档 120 点）：

| 探针（粗/细） | 吻合 |
|---|---|
| 满探针 16/64 | **120/120**（每条 `cos` 也逐位一致） |
| 2/8 | 120/120 |
| 2/4 | **0.958** ← **低于 0.98** |
| 1/2 | 0.725 |

⇒ 能当**实现性质**断言的只有一条：**探针吃满 ⇒ 必须 1.0**。已按此写成断言（另配「探 1/1 时两者必须不同」的反向对照）。
要在生产语料上复现 0.98，需要 200/10,000 中心 + 100 万行 ⇒ 测试里做不到。

## 六、接手须知（四条最容易踩的）

1. **`queryEmbedding` 是向量路唯一的开关。** 不传 ⇒ 整段不执行（`ran=false`），而且**连端口的四态判定都不发生**
   （实测：不传 3 条 SQL / 全表 COUNT 0 次；传了 6 条 / COUNT 1 次）。改这条路径前先读设计 **D2**。
2. **端口每次现场装配、不缓存**（**D1** / **D1-a**）。缓存会让 `route()` 用新探针数、`search()` 用构造时的旧值 ⇒ 桶集分叉且不报错。
   注意实现是「**带向量的**召回才装配」（设计字面写的是「每次」）—— 若你按字面改回无条件装配，D2 的**成本**维度会静默破掉。
3. **`inhibitionTrace` 与 `recall` 共用一个流水线** ⇒ 想让 `baseScore` 与 `Hit.score` 逐位相等，**两边必须传同一条 `queryEmbedding`**（**D8**）。
4. **改向量路相关测试前先读 §3.2**：时间窗在默认参数下与归档线同边界，用「1 条旧 + 1 条新」去测它**会得到一条恒绿断言**。

| 2 | **R6（召回路径 · 探针 20/50 · n=1000）** | max **12,782 行**（mean 4,502.959 / p50 4,385 / p99 10,103 / min 57） | ⚠️ **不设门槛**（观测值） | ⚠️ **不判红绿**；**读数仍红（6.39 倍）** |
| 3 | **召回两档**（同机、同次运行、背靠背） | **old-path**（不传向量）mean **14.261 ms** / p99 **78.624 ms**；**new-path**（传向量）mean **143.770 ms** / p99 **370.120 ms** | 参考线 ≤ 200 ms | old-path **过参考线**；new-path **若按同一参考线则不过**（⚠️ 参考线不是硬门槛） |

⇒ ★ **「实测 ≡ 推算」已在 100 万条规模确认**：R6 的 `candidateReadRowsBasis.mode` 由 `derived` → **`measured`**，
而七个数值与推算值**逐位一致**（连 `mean 4,502.959` 都一致）⇒ **此前只在 1 万条规模核过**。
⇒ ⚠️ **但它不改变判定**：`measured` 与 `derived` 同值 ⇒ **该红的照旧红**。

### 7.2 new-path 的 143.8 ms 归因（**别读成「向量路本身慢」**）

- 每次查询读 **约 4,503 行 × 3 KB ≈ 13.5 MB** 向量；实测 `perRowReadCostUs = 35.491`
  ⇒ 4,503 × 35.491µs ≈ **160 ms** ≈ 实测 143.770 ms ⇒ **延迟是候选行数的直接后果**；
- ⚠️ `recallVectorPath.vectorScanShareOfNewPath = 1.1116`（**111.16%**）⇒ **> 100%，此占比不可当结论**
  （分子是「独立跑一遍向量扫描」、分母是「整条召回」⇒ **不是同一次调用**）⇒ **只作存在性参考**；
- ⚠️ **「向量扫描本身」（`vectorRouteP99Ms` = 428.704 ms，直接调 `route() + search()`）
  与「整条召回」（143.770 ms 均值）是两个量** ⇒ **不可互换、不可相加**。

### 7.6 ★ 一条**记账订正**（2026-11-04 · 关于「门禁输出里的 ✗」）

T03 提交的 message 里我写过一句「`check:params` / `check:doc-counts` 打印的 `✗ 发现 N 处参数计数不一致`
来自 `audit:negative-control` 的故意变异」——**这句是错的**（T03 已推送，按纪律不改写历史，在此订正）。

**实际来源（已核）**：那是**单元测试里的负控**故意打到 `stderr` 的 ——
`tests/contracts/doc-counts.test.ts:137` 喂一份写着「**55 项**」的坏文档（真值是 60），
断言 `runCli([...])` **退出码 ≠ 0**；那句 `✗` 的文案出处是 `scripts/check-doc-counts.ts:454`。

⇒ ⇒ **它不是「不红的自检」，而是一条正在工作的负控**（正控：真文档 → 只出 ✓、`exit 0`；
已实测：`pnpm run check:params` 对真文档只有一行 `✓ §5 表与 DEFAULT_PARAMS 逐键逐值相等`、`exit 0`）。
⇒ **读门禁日志的正确姿势**：`pnpm run verify` 里 `stderr` 上的 `✗` **不等于失败**，
失败与否只看**进程退出码**；而负控的 `✗` 恰恰是「它有判别力」的证据。
