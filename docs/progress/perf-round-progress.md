## 二、目标 1：细层分组改成一次分堆

### 2.1 改了什么

**旧写法**（`buildCentroidModel` 的细层）：

```
for 每个粗桶:
    for index 从 0 到 N-1:                    ← 每个粗桶都从头扫一遍全部向量
        if assignments[index] == 粗桶: 收进本桶
```

**新写法**：先一次性把向量按 `assignments` 分堆（`O(N)`），再按粗桶顺序训练细层。

### 2.2 结果等价的证据（**不是「看着一样」**）

`tests/unit/ivf.test.ts` 新增两条**成对**用例：

| 用例 | 判据 |
|---|---|
| 「单遍分堆必须与旧双层扫描逐位等价」 | 把**旧的 O(粗桶数 × N) 写法原样重写**成参照实现（在测试里，不复用被测代码的分堆）⇒ 两边**每一个细中心逐位相同**（`Float32Array` 逐元素 `toEqual`，不是 `toBeCloseTo`） |
| ★ **负控** | 把参照的**输入顺序反过来**再算一次 ⇒ 中心**必须不再相同** ⇒ 证明上一条判据真的对**顺序**敏感（否则它只是「两边跑了同一个函数」） |

⚠️ **为什么要逐位**：细层的初始中心取自「该粗桶的**前 `finePerCoarse` 条**」
⇒ 分堆只要**改变了桶内顺序**，初始中心就变，浮点结果就变。这条正是这次改写最可能出错的地方。

### 2.3 实测收益（隔离测量，**不含 k-means**）

口径：200,000 条向量 · 200 个粗桶（`assignments` 均匀分布）· 只测「按归属分堆」这一步。

| 写法 | 第一遍 | 第二遍 |
|---|---|---|
| 旧（每桶扫全量，**4,000 万次比较**） | **87.0 ms** | 83.3 ms |
| 新（一次分堆） | **7.1 ms** | 3.2 ms |

⇒ **约 12 倍**（该步骤）。⚠️ **别把它读成「重训快了 12 倍」**：k-means 本身是
`O(迭代轮数 × N × K × D)`（每轮都要对全部向量算到 K 个中心的点积），远大于「分堆」这一步。
**诚实的说法**：百万级下这一步省下的绝对时间是**百毫秒量级**（1,000,000 × 200 ⇒ 约 0.4 s → 约 0.03 s），
是「去掉一个本该 O(N) 的活」的清理，不是「重训变快一个数量级」。

## 三、目标 2：`maxIterations` 透传

### 3.1 改了什么

- `BucketRebuildOptions` 新增 `maxIterations?: number`（内部选项）
- `RebuildBucketsOptions` 新增 `maxIterations?: number`（公开方法参数）
- 两处都用**条件展开**（`exactOptionalPropertyTypes`：显式塞 `undefined` 与「不传」是两件事）
- 真正到达：`maintain.rebuildVectorBuckets` → `rebuild.ts` → `buildCentroidModel` → `sphericalKmeans`

### 3.2 为什么它**不进 `Params`**

`Params` 描述的是「**这个库怎么算**」（改它要记 `config` 事件、会影响历史数据的解读方式）；
而 `maxIterations` 是「**这一次重训怎么跑**」⇒ 只能是**调用期**入参。
⚠️ 它也**不进事件 payload**（§8.4 硬规则 4 写死 `action='rebuildBuckets'` 的字段集只有 `cells, members`）。

### 3.3 判据怎么选（**这一步踩过坑，记下来**）

最初的想法是「传 1 轮 vs 25 轮 ⇒ 中心不同 ⇒ 说明透传成功」。
**实测**：这份夹具在 **1 轮就收敛**，1 轮与 25 轮的中心**逐位相同**（探针实测四个取值 `1/2/3/5/25`
与默认值指纹一致）⇒ 那条判据会写成**恒绿断言**。

⇒ 改用**与数据无关**的判据：`sphericalKmeans` 对非法 `maxIterations` 有守卫
（`kmeans.ts:68` 抛「必须是 ≥ 1 的整数」）⇒ **传 `0` 必须抛**，而**不传必须不抛**（成对）。
值只有真的到达训练层，那条守卫才会响。

### 3.4 收益

百万级重训可以显式压低迭代轮数（例如 `1~3`）来换**更小的峰值内存与更短的阻塞时间**，
代价是**中心可能没收敛**。这正是 `docs/progress/stage3-progress.md` §3.1 缺陷① 的原始诉求
（「没法用降迭代换内存 ⇒ 只能被 OOM 打断」）。

## 五、目标 4：只补跑迁移段（`scripts/migrate.ts`）

### 5.1 它解决什么

v1 → v2 迁移分两段：**A** 建表建索引（全 `IF NOT EXISTS` ⇒ 可重复执行）、
**B** 回填 `archival_schedule`（**分批提交**）。**B 跑到一半崩了**是真实场景：
库里是「A 完成、B 只回填了一部分」的中间态。

此时正确的动作只有一条：**只重跑 B**。以前这件事要么跑完整的 `migrateV1ToV2()`（幂等，但显得像从头来），
要么手工敲 SQL ⇒ 现在是一条命令：

```bash
pnpm migrate --db data/ocean.db --dry-run      # 只看现状（只读打开，写不进去）
pnpm migrate --db data/ocean.db --phase b      # 只补跑回填段
pnpm migrate --db data/ocean.db --phase all    # 完整两段
```

### 5.2 判据设计（三个「不宽容」的取舍）

| 取舍 | 理由 |
|---|---|
| **缺 `--db` 直接抛错**（不猜默认路径） | 猜错就是往**另一个库**写；与 `scripts/backup.ts` 同款纪律 |
| **非法 `--phase` 抛错**（不静默回退 `all`） | 迁移**不可逆** ⇒ 「我以为只补跑 B，结果它把 A 也重跑了」不值得用宽容解析去换 |
| **`--dry-run` 用 `readonly: true` 打开** | 比「记得别写」可靠：就算代码写错也写不进去 |

### 5.3 断点续跑的测试（`tests/integration/migrate-script.test.ts`，11 条）

- ★ 造「A 完成、B 只回填了 2 行、`archival_schedule_ready=0`」的中间态
  ⇒ 只跑 `--phase b` ⇒ 断言回填补齐（行数 == 活记忆数）且就绪位回 1
- **幂等**：再跑一次 ⇒ 行数不变
- ★ **干跑真的没写**：库文件 **sha256 前后相同**（不是「看返回值说没写」）
- ★ **反例**：中间态干跑 ⇒ 报告必须说「走逐行精筛」，**不许**说「回填完整」

⚠️ 测试里踩到一个坑值得记：`ensureSchema()` 在**首次建库**时也会顺手回填
⇒ 造中间态必须**显式** `DELETE` 再插 2 行，不能用「删掉多余的」那种写法（起始行数不确定）。
