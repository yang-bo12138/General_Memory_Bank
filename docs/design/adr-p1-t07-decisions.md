## 1. D-1 便利查询函数：**保留，但独立**

**裁决**（主理人拍板 ①）：库**可以**提供「按上下文匹配已知实体名」的辅助函数，但

1. **独立**：**不在** recall 流水线里（流水线只做「名字 → id」的归一）；
2. **显式**：只有**调用方主动调**它才算数（调用方自己决定要不要用）；
3. **成本写在脸上**：文档必须写明成本 = **每次调用 O(#实体 + #别名) 行扫描**
   （子串匹配 ⇒ 短名/英文短词会误命中，无词边界）；
4. ⚠️ **阶段 1 不实现它**：它不在 §12 阶段 1 的方法清单里 ⇒ 实现它会把阶段 1 的范围扩到清单之外。

**理由**（与 ADR-2 / 成本模型 / 步骤 0 的耦合三条同源，见 `adr-p1-t08-gaps.md` §1.3）：
摘要是「**别让后人以为它不存在**」——设计稿留口子，实现阶段另议。

## 2. D-2 §9.3.0.1 的措辞：**主理人的读法成立，我的「四项独占」写法已被取代**

**裁决**（B）：§9.3.0.1 首句改成

> **在写入路径内，§4.9 步骤 2 / 3c 的合并写入序列是唯一能改变这六项的代码路径**：
> `content` / `content_hash` / `embedding` / `growStability` 加固 / `content_history` 归档 / `merge` 事件。

**我要认领的一处**：我上一轮（ADR-P1-R2 的 R-5）把它改成了「**四项**（不含 `embedding` 与 `growStability`），
并写「步骤 2 不走合并序列」——**这一点与原文不符**：原文第二段本来就写着
「**前台写入（§4.9 步骤 2 / 3c）**、去重路径、后台补齐扫描全部走它」，
⇒ **步骤 2 本来就在这条路径上**，我的改写把读者引向了一个错误的例外。**已按 D-2 改回，并把六项清单恢复。**

**但我保留一处限定（并写进了正文）**：「**写入路径内**」这四个字不可省——
**`touch()`（§4.2）也加固**，它同样调 `growStability()`。
⇒ 逐字读「唯一能改变这六项的代码路径」而不加限定，就是**假命题**。
⇒ 正确表述是两句：
- 「**写一条记忆时**，正文/向量/稳定度/历史/事件只由合并写入序列改」（本节管这个）；
- 「**稳定度只由 `growStability()` 改**」（§4.2 / §4.15.5 的另一条通则，管 `touch()` 这条路）。

**同时写死的一条实现事实**：`UPDATE memories SET embedding` **全库只应出现在一个模块里**
（当前实现：`src/store/merge.ts`）⇒ 可用**静态扫描**守住；
步骤 2 碰 `embedding` 的唯一入口是「**向量回填**」——**只补 `embedding IS NULL` 的行，已有向量不得覆盖**。

## 3. D-3 ~ D-7 写路径的五条口径（工程师-4 自行定的那六条，签字版）

| 裁决 | 要点 | 关键理由 |
|---|---|---|
| **D-3** | `entityAliases[].name` 走与 `input.entities` **同一套 a→b 归一**；未命中 ⇒ **按步骤 1b 新建**，且**新建的实体计入 `@linkedEntityIds`** ⇒ 与本条记忆**建立关联**；命中既有但不在 `input.entities` 里的 ⇒ **不自动计入** | §4.9 步骤 1b 写明「`@linkedEntityIds` = a 返回的 id 与 **b 新建的 id** 汇总」⇒ b 步产物天然在集合里；且「**新建即孤儿**」（为这次写入而建的实体却不与这次写入关联）是不该有的状态。**反转了我上一轮的「建但不链接」**（那会让调用方声明的别名在召回里派不上用场） |
| **D-4** | tie-break 必须是**全序**：`entityOverlap 降序 → cos 降序（null 排最后）→ raw_bm25 升序 → id 升序` | §12 对排序的要求是「排序有全序 tie-break」；**没有 `id` 升序就不是全序** ⇒ 同样输入不可复现。而合并是**不可逆**的正文改写（只能靠 `content_history` 兜底）⇒ 复现性不是小事 |
| **D-5** | `alias` 撞任何既有主名（含撞自己）⇒ **冲突**；**两条路径分别处理**：`setAlias` ⇒ `CONFLICT`（`details.conflictingEntityId`）；**写路径步骤 1c ⇒ 跳过 + `warnings` + 磁盘日志，不抛错** | §4.5 的解析顺序是「主名优先」⇒ 同一字符串会解析出两个答案 ⇒ 这种状态必须被禁止存在；而写路径**抛错会让调用方重试 `write()`** ⇒ 同一事实被写两遍（§11.2 末：别名冲突是「非致命但调用方必须知道的事」） |
| **D-6** | 退化态（候选不足 2 个 bigram）⇒ **精确判定式**见 §0.1 D-6；`cos` 通道**整条不生效** | 字面读法：步骤 3a 的「**应要求实体重叠数 ≥ 2 才允许合并**」是**必要条件**，叠加步骤 c 的「满足任一即可」⇒ 退化态判定**收敛为** `entityOverlap ≥ DEDUP_ENTITY_MIN`。候选面已不可信 ⇒ 不能拿余弦去合并；**也不得放宽阈值**（短文本的误合并率会直接跳上去） |
| **D-7** | 三类越界 ⇒ `INVALID_INPUT`；**`details` 一律平铺**：`reason` = `'confidence'` / `'kind'` / `'media'` | 与 §4.9 步骤 2 的向量校验同口径（`details.reason` = `'dim'`/`'nan'`/`'zero'`）⇒ **本库的错误 details 一律平铺**（`MemoryErrorDetails` = `Record<string, unknown>`），嵌套形状会让调用方写两套取值逻辑（C36）。且 `confidence` **有**库层 CHECK ⇒ 不在应用层硬拒就会漏裸 SQLite 错误码（§11.2）；而 `emotion` **没有**库层 CHECK ⇒ **钳制**（§4.3）——**两者别写混** |

## 4. D-8 `entityIds` 与 `entityNames`：**互斥**

**裁决**（主理人拍板 ②）：与 ADR-P1-T08-GAP 的口径一致，此处只做**确认**：

- **同时给 ⇒ `MemoryError.INVALID_INPUT`**（理由：两者装的是同一件事的两个阶段，取舍 = 静默丢弃调用方的一半意图；
  且「`[]` = 明确无实体」的语义只在互斥时才无歧义）。
- **两者都不给 ⇒ 图谱路为空**（退化为文本路 + 向量路）——ADR-2 明写并接受的代价。
- 库内**不得**出现「拿 context 扫 `entities` / `entity_aliases` 表」的代码（三条理由见 `adr-p1-t08-gaps.md` §1.3）。

## 8. 我没有把握、需要进一步确认的部分

1. **D-3 的「命中既有但不在 `input.entities` ⇒ 不计入 `@linkedEntityIds`」是个半截规则。**
   调用方写 `entityAliases: [{ name: '张三', aliases: ['老张'] }]` 且**不**把张三放进 `entities`，
   而张三**已存在** ⇒ 别名挂上了，但**这条记忆不与张三关联** ⇒ 图谱路查不到它。
   ⇒ **边界（明写）**：想让「这条记忆关于它」成立，**必须把实体名写进 `input.entities`**。
   但这条边界对调用方不够显眼 ⇒ **是否要把「命中既有但未声明关联」也报一条 warning**？
   （`WriteWarning` 现在只有 `ALIAS_CONFLICT` 一种 ⇒ 加一种就是**扩 §6 的公开类型** ⇒ 走 ADR。
   我给的默认值是**不加**，因为「没写进 `entities`」本身就是调用方的声明。）
2. **D-7 的 `details` 平铺形状会让「同时有两种错」的输入只暴露第一个。**
   `kind` 非法 **且** `confidence` 越界 ⇒ 只报 `reason='kind'`。
   两种错都在时，调用方要改两轮。⇒ 可选方案：收集全部错误再一次抛（但那要先跑完全部校验，
   与「校验放最前面、失败即抛」相冲）。**我给的默认值是「先到先抛」**，与 §4.9 步骤 2 的向量校验一致。
3. **D-4 的 `raw_bm25 升序` 这一级依赖 FTS 的 `bm25()` 方向**（负值，越负越相关 ⇒ 升序 = 最相关在前）。
   若将来 `raw_bm25` 的口径变（例如改成绝对值），这一级的含义会**静默反转**。
   ⇒ 建议实现时在代码注释里写死「`raw_bm25` 是负值 ⇒ 升序」这一前提。
4. **D-9 的「`stats` 的基线断言顺延」需要有人认领**：它顺延到阶段 4（`stats` 归阶段 4），
   ⇒ **P4 的任务清单里要有一行「`stats` 的基线断言」**，否则这一条会在阶段 4 漏掉。
   ⇒ 交给 team-lead 记一笔。
5. **D-12 的「先对账后开路」时点**：我写的是「在启动对账 / 首次重训的全量重分配之后、对外提供 IVF 向量路之前」。
   若阶段 2 的实现顺序是「先开路、再异步对账」⇒ 这条硬断言会与实现冲突 ⇒ **它其实是一条顺序约束，不只是断言**。
   ⇒ 需要阶段 2 的实现者确认顺序。
