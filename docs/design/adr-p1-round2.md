## 2. `software-engineer-2` 的三点

### 2.1 ① `memoryId` 自校验漏了 `AND deleted = 0` —— **追认（主线上已落地）**

**裁决：必须加，理由与设计稿逐字一致。**

- §4.5 步骤 4 的逐字要求：「传了 @memoryId 时必须先
  `SELECT 1 FROM memories WHERE id = @x AND deleted = 0`；查不到 → 抛 `NOT_FOUND`（details.missingIds）」。
- **外键只管「行在不在」，不管「行是不是已被软删」**：
  `edges.memory_id REFERENCES memories(id) ON DELETE SET NULL`（§3）⇒ 软删的行**仍在表里**，
  外键照过 ⇒ 漏掉这个条件 = **一条已被遗忘的记忆继续给图谱供能**，
  且它迟早被 §4.10 的 sweep 硬删 ⇒ 那时这条边的 `memory_id` 会被 `SET NULL` 成「无证据断言」——
  **调用方当初要的是证据，结果拿到一条没有证据的边**。
- 还要与 `touch()` 一致：§4.2 的 touch 校验软删 id 时用 `AND deleted = 0` ⇒ **软删的记忆不是有效记忆**
  （§4.6 的准入闸门一律 `deleted = 0`）。

**状态**：主理人已以 `e1b1eef fix(P1-T05): memoryId 自校验补 AND deleted = 0（软删记忆不可作边证据）` 落地，
并已合并进工程师-2 的分支（`6657fdb`）。该 commit 还带了**负控实测**
（去掉 `AND deleted = 0` ⇒ 新增的 2 条软删用例立刻变红）⇒ **守卫是真的守得住**。

⇒ **本轮不需要任何新改动**；我只需把这条口径的**理由**补进本文件（避免下次又有人按「外键兜底」的直觉删掉它）。

### 2.2 ② 自校验与自环校验的**次序** —— **裁决：认可现状（`memoryId` 先、自环后）**

**裁决口径（已写进 §4.5 步骤 1 尾部）：**

> 校验次序写死为五步：
> ① 两端名称解析（只读）→ ② `memoryId` 存在性自校验（只读，`AND deleted = 0`）
> → ③ 步骤 2 建实体（**写**）→ ④ 自环校验（必须在 `@subjectId` / `@objectId` 回填之后）
> → ⑤ 步骤 3 UPSERT（**写**）。

**理由（不是「随便哪个都行」，而是一条可复用的原则）：**

1. **自环校验结构上必须在解析之后**——它比较的是两个 `entity_id`，
   而 `entity_id` 要等端点解析（步骤 1）与建实体（步骤 2）之后才齐备（§4.5 明写「按 id 判不按名判」）。
   ⇒ 也就是说，**自环校验是本流程里唯一一个「不能提前」的校验**。
2. ⇒ 把**唯一能提前的只读校验**（`memoryId` 存在性）提到所有写入之前，
   是**唯一能做到「失败时零副作用」**的位置（连回滚都不需要，更不会留下「为一次注定失败的 link
   顺带建出来的孤儿实体」——§4.5 步骤 2 末尾专门警告过这个坑）。
3. **代价明写**：同时传「坏 `memoryId`」与「自环」时，**先报 `NOT_FOUND`（memoryId 不存在）**，
   而不是 `INVALID_INPUT`（自环）。这是**有意为之**，不是偶然——
   一次只暴露一个错误，两个都得改，但一次改一个。

⇒ **实现的现状**（`src/store/link.ts` L165-188 注释写的是「步骤 1 尾部」）**符合本裁决**，**不用改代码**；
需要做的只是**把这条次序写进设计稿**（已做）。

### 3.1 ②B 「唯一合并写入点」与步骤 2 回填的措辞

> ⚠️ **本节的「四项独占 + 步骤 2 不走合并序列」写法已被 `adr-p1-t07-decisions.md` D-2 取代。**
> 原文第二段本来就写着「前台写入（§4.9 步骤 2 / 3c）……全部走它」⇒ **步骤 2 本来就在这条路径上**；
> 现行口径是「**在写入路径内，步骤 2 / 3c 的合并写入序列是唯一能改变这六项的代码路径**」，
> 六项清单**保留**，另加「写入路径内」这个限定（`touch()` 也加固）。
> 下面的原文保留作为**决策留痕**。

**裁决：认可实现结构；设计稿 §9.3.0.1 的措辞有缺陷，已勘误。**

- **实现结构认可**：合并序列与向量回填都放在 `src/store/merge.ts`
  ⇒ 「唯一写入点」可以靠**扫描该模块之外没有第二处正文 UPDATE** 来守住，而不是靠注释提醒。
  ⇒ 这与 §9.3.0 的 `assignBucket` / `unassignBucket` 是**同一种手法**：
  **把「唯一写入点」从「一条纪律」变成「一个只有它能碰的地方」。**
- **§9.3.0.1 的原措辞有两个缺陷**（已勘误）：
  1. **「六项」清单里的 `growStability 加固` 不由本节独占**——`touch()`（§4.2）与 §4.9 步骤 2 的
     完全重复**也都加固**。**加固的唯一入口是 `growStability()` 本身**（§4.2 / §4.15.5）。
     ⇒ 本节该管的是「**正文 / 哈希 / 历史 / merge 事件只由合并序列改**」；
     「**稳定度只由 `growStability()` 改**」是**另一条**通则。
     （把两件事塞进同一张清单，会让人以为「只有合并能加固」——而 `touch()` 明明也能。）
  2. **「前台写入（§4.9 步骤 2 / 3c）……全部走它」过宽**——**步骤 2（完全重复）不走合并序列**：
     它不改正文 / 哈希 / 历史、不发 `merge` 事件；它做的是「加固 + 补齐实体关联 + **向量回填**」。
     ⇒ 正确表述：**步骤 3c 走合并序列；步骤 2 只通过 `merge.ts` 里的回填函数碰 `embedding`**，
     而回填函数**只补 `embedding IS NULL` 的行、已有向量不得覆盖**。
- **代价（明写）**：合并把 `embedding` 置 NULL 时（没传新向量），
  该记忆**暂时退出向量路**（文本路与图谱路仍可召回）——
  这是**刻意**的：留着旧向量 = 造一条「语义指向已不存在的内容」的记录，**且不报任何错**。

### 3.2 ②C 别名目标实体不存在时建不建

> ⚠️ **本节的「建、但不进 `@linkedEntityIds`」结论已被 `adr-p1-t07-decisions.md` D-3 取代（反转）**：
> 现行口径是「**建，且新建的实体计入 `@linkedEntityIds`**（⇒ 与本条记忆建立关联）」；
> 「命中既有实体但不在 `input.entities` 里」的那一个仍**不自动计入**（关联未被声明）。
> 下面的原文保留作为**决策留痕**。

**裁决：建，但**不进 `@linkedEntityIds`**；并写明一条边界（已落 §4.9 步骤 1c）。**

- **建**（不静默丢弃）：`entityAliases[].name` 是调用方**显式点名**的一个实体，
  而写路径的既定语义就是「写入路径负责建实体」（步骤 1b 对 `input.entities` 里的未知名字也是建）
  ⇒ **同一个调用方语义在两个字段上必须表现一致**。
  替代方案「不建」会让这次声明的别名**无处可挂** ⇒ 静默丢弃 ⇒ 违背本节「不要静默」的总原则。
- **不链接**：`@linkedEntityIds` 的定义不变（= a 步与 b 步的结果汇总，**只来自 `input.entities`**）。
  ⇒ `entityAliases` 只声明**命名**（谁是谁的别名），**不声明关联**（这条记忆关于谁）；
  关联只由 `input.entities` 决定。
- **由此产生的一条边界（已写进设计稿）**：调用方若只声明 `entityAliases` 而**没把该实体名放进
  `input.entities`**，则别名映射建好了，但**本条记忆不与该实体关联**
  ⇒ 图谱路（§4.6 步骤 2b）查不到它。
  ⇒ **想让别名对召回生效，必须把实体名同时写进 `input.entities`。**

### 3.3 ②D 多候选选取规则

**裁决：认可（重叠数 → 余弦 → 文本路序），并把这条写进 §4.9（原稿没写）。**

- 原稿只写「判定成立则进入原子合并」，**没写选谁** ⇒ 实现者各自发挥 ⇒
  同一份输入在不同实现里会合并到**不同的记忆**（且不报错）。
- 规则：**实体重叠数多者优先；重叠数相同则余弦大者优先；再相同则取文本路排序靠前者**
  （`FIND_CANDIDATES_SQL` 有 `ORDER BY bm25(mem_fts) ASC` ⇒ 第三层是**确定的**，不是随机的）。
- ⇒ 规则**确定**（同样的输入永远合并同一条）⇒ 重放与复现不会漂移。
- **不要**改成「取第一条达标的就合并」：那会让「先命中哪个候选」取决于 BM25 抖动，
  而合并是**不可逆**的正文改写（只能靠 `content_history` 兜底）。

### 3.4 ②E `alias` 等于（自己的）主名

**裁决：认可「算冲突」，没有例外**（已写进 §4.9 步骤 1c）。

- §4.9 步骤 1c 原本就要求「校验 a 不等于任何已有 `entities.name`（主名优先）」，
  但**没说「撞自己」算不算** ⇒ 实现的「撞自己也算」是**对的**。
- 理由：§4.5 的解析顺序是「主名优先」⇒ 同一字符串会解析出两个不同的答案
  （① 命中主名 A、② 命中别名 B）⇒ 召回结果取决于实现先查哪张表 ⇒ **必须禁止这种状态存在**。
- 与 `setAlias` 同口径（它也不允许把主名写进别名表）⇒ **两处不能统一**的地方要统一。

### 3.5 ②F §4.9 步骤 3a 的退化条款

**裁决：认可实现口径；设计稿的字面「≥ 2」要改成参数口径**（已勘误）。

- 实现口径：候选不足 2 个 bigram（`tokens.length < 2`）⇒ **文本路退化**
  ⇒ **余弦判据整条不生效**，只认**实体重叠**（且用参数 `DEDUP_ENTITY_MIN`，默认 2）。
- 设计稿的字面「实体重叠数 ≥ 2」是 `DEDUP_ENTITY_MIN` 的**默认值**，
  判据本身应当用**参数**（与步骤 c 的实体判据同源）⇒ 已勘误。
- ⚠️ 补充一句容易写反的地方：退化态下**不是**「两条判据里有一条成立就合并」，
  而是「**只认实体重叠**」——候选面已不可信 ⇒ 不能拿余弦去合并。

### 3.6 ②G `confidence` / `kind` / `mediaRef` 的应用层前置校验

**裁决：认可；并把「`confidence` 越界 ⇒ `INVALID_INPUT` vs `emotion` 越界 ⇒ 钳制」的不对称写进 §6。**

- 前置校验的**必要性**：`memories.kind` / `media_type` / `confidence` 都有**库层 CHECK**
  （§3：`CHECK (confidence >= 0.0 AND confidence <= 1.0)` 等）
  ⇒ 不在应用层拦就会撞 CHECK ⇒ `translateSqliteError` 对**清单之外**的错误码**原样抛出**
  ⇒ 调用方拿到一个**未类型化**的错误（违反 §11.2「客户端只看到规范化的错误结构」）。
- **为什么 `confidence` 报错而 `emotion` 钳制**（这两条长得很像，但口径刻意不同）：
  - `confidence` **有**库层 CHECK ⇒ 应用层必须拦，且应当**报错**；
  - `emotion` **没有**库层 CHECK ⇒ 钳制是它的既定语义（§4.3 / §6 明写「越界值由 §4.3 钳制」）。
  - ⚠️ **「不信任调用方」= 报错，不是替他改成合法**：
    钳制 `confidence` 会**静默改写**调用方的数据，而调用方以为自己写进去了。
- 顺带把 `mediaType` 的枚举校验也写进了实现（§3 的 CHECK 同样是库层的）⇒ 一并认可。

## 4. 阶段 2 交接：一条必须写进 P2-T03 验收标准的硬边界

工程师-4 提了一个**他自己发现的边界**，我确认它成立，并给它一个明确的兜底：

> 他的静态断言只保证「**阶段 1 不写桶**」，**不保证「阶段 2 写了」**——
> 阶段 1 → 2 之间没有任何代码路径调用桶分配 ⇒ 若 P2-T03 忘了接上，静态断言**不会报警**。

**裁决**：这条边界**由阶段 2 的「集合相等」硬断言兜底**，但**必须满足一个条件**：

> 集合相等的**左侧必须是「全部 `embedding IS NOT NULL` 且 `deleted = 0` 的记忆」**，
> 而不是「本次批次里带向量的记忆」。
> ⇒ 只有前者才能在「阶段 2 压根没写桶」时**立刻变红**（左侧全体 vs 右侧空集）。

⇒ **交给 team-lead 的执行项**：P2-T03 的验收标准里，那条集合相等硬断言要**写明比较的是哪一侧**。
（若只写「本批次内集合相等」，它会**假绿**：阶段 2 什么都没写时，两边都是空的 ⇒ 相等 ⇒ 通过。）

这正是 ADR-P1-C 冲突 7 裁决里「阶段 2 两条硬断言」的**第一条**，本轮只是把它的**措辞收紧**。

   代价是 `@linkedEntityIds` 的定义要变（它现在严格等于「`input.entities` 的解析结果」）。
   ⇒ **需要 team-lead 确认产品意图**：别名声明要不要隐含「这条记忆关于它」。

   只是「谁有库层 CHECK」的副产物。⇒ 若将来 `emotion` 也加了 CHECK，要不要统一成报错？

3. **R-2 的次序代价**（同时坏 `memoryId` + 自环 ⇒ 先报 `NOT_FOUND`）：
