## §0 TL;DR

1. **两个红是同一个成本源。** 写路径 `2,184 行 → 39.12ms`、读路径 `4,503 行 → 159.81ms`，
   两条都等于「`nprobe` × 每桶活行数 × 每行把 3KB 向量取回来的成本」。
   **写路径看行数上限（H1：`≤ 2,000`），读路径看毫秒（R1/R3：现状 §5 没有独立 SLO）。**
2. **行数有两个可动因子**：`nprobe`（质量闸门 —— `DESIGN-v2-errata.md:2079` / `DESIGN-v2.md:3842` 明写它是**召回损失的唯一来源**）与**每桶活行数**（桶粒度，需重训 111 分钟）。
   只动前者 ⇒ **用质量换延迟**；只动后者 ⇒ **行数均值不变**（§3 L5）。
3. **H1 的 2,000 行预算在当前结构下结构性不可达**：`2,000 ÷ 20 = 100 < 平均桶容 100.34`
   ⇒ 即便哈希级完美均衡、一行不倾斜，写入侧也是 `20 × 100.34 = 2,006.8 行 > 2,000`（复算见 §2.3）。
   ⇒ **H1 必须靠「减 nprobe」或「减少每次读的行」二者之一才能绿，没有第三条路。**
4. **三档各付什么**：
   - **A（只调参）**：H1 绿（`5,521 → 1,932`⚠️推断），**代价 = 去重漏检率（未测）**；**一天内可出数**。
   - **B（A + 聚簇存放）**：延迟掉 1.3~10 倍（区间宽，**不可外推定档**），**H1 的绿法没变**（仍靠 A 的质量代价）。
   - **C（B + 两段式）**：**唯一「H1 绿且质量不降」的路线**；但它**不自动让 H1 变绿**，需要先裁决「H1 的行是什么」（§5 ③），否则会出现「实现了、判据不认」或更糟的**假绿**（§3 L4 与附录 B）。
5. **最容易被误读的一处**：`78.62ms` 是 **R4（不含向量路 · 现状口径）**，它**不是**召回延迟；
   「召回延迟」在向量路成为产品默认之前**是未测**，不是「78.62ms」。

## §2 根因：一个共用量，两种投影

### 2.1 可复算式

```
单次调用耗时 ≈ 命中行数 × 每行取回成本
命中行数     = nprobe × 每桶活行数        （桶倾斜时取「命中桶的活行数之和」，不是 nprobe × 均值）
每行取回成本 = 散页读（3,072B 向量 + 行内正文）× 介质惩罚
```

逐个因子代入实测（全部可复算，命令见 §7）：

| 路径 | 式子 | 结果 | 结论 |
|---|---|---|---|
| 召回 new-path（向量扫描段） | `4,502.96 行 × 35.491 µs` | **159.81ms** | **恰好等于** `vectorRouteLatency.meanMs`（159.8145）⇒ 耗时**几乎全部**是「把 3KB 向量逐行取回来」的随机读 |
| 写入去重（向量扫描段） | `2,184.03 行 × 17.912 µs` | **39.12ms** | 等于 `writeSegments.vectorCandidateScan.meanMs`（39.1198） |

> ★ **推论（⚠️推断）**：768 维点积本身（4,503 × 768 ≈ 3.46M 次乘加）**在噪声内**。
> 证据：两个独立采集轮里，「行数 × 单价」都精确复现了实测均值，剩余量级 ≤ 1ms。
> ⇒ **优化 CPU 无用，必须优化「取回的行数」或「取回的字节 / 顺序性」。**

### 2.2 两个可动因子，只有一个是质量闸门

| 因子 | 动它 = 什么 | 是否质量闸门 | 是否需要重训 |
|---|---|---|---|
| `nprobe`（`NPROBE_FINE=50` / `NPROBE_WRITE_FINE=20`） | 少探几个桶 | **是** —— `params.ts:124` + `DESIGN-v2-errata.md:2079`：**召回损失的唯一来源** | 否（改参数即生效） |
| 每桶活行数（由 `ROUTER_FINE_CENTERS=10000` 与 k-means 均衡度决定） | 桶更小更匀 | 是（更细的桶 = 同 nprobe 下覆盖体积更小，损失结构类似降 nprobe） | **是（111.1 分钟/次，D14）** |
| （隐式第三因子）行内字节 / 物理顺序 | 同样多的行，取回更便宜 | **否** | 否（改布局，不回训） |

### 2.3 ★ H1 的 2,000 行是**结构性**预算，不是「倾斜造成的偶发超标」

```
平均桶容 = 1,000,000 ÷ 9,966 = 100.34 行/桶          （D11 的 trainedMembers/trainedCells）
写入侧预算/桶 = 2,000 ÷ 20 = 100 行/桶              （H1 门槛 ÷ ROUTER_NPROBE_WRITE_FINE）
⇒ 100 < 100.34  ⇒  即便桶**完美均衡到均值**，写入侧也是 20 × 100.34 = 2,006.8 行 > 2,000
```

**这解释了三件事，而且三件事必须一起说**：
1. **桶倾斜只是把 2,006.8 放大到 5,521（2.76 倍）**，倾斜不是**根因**；
2. 所以 **L5（桶均衡）单独永远不能让 H1 变绿**（§3 L5 有定量）；
3. 所以 **H1 要么靠减 `nprobe`（L1，用质量换），要么靠减少每次读的行（L4，用实现换）** —— 没有第三条路。

### 2.4 ★ 结论：H1/H2 与召回延迟是**同一个量的两种投影**

| | 写入去重路径（H1/H2） | 召回向量路（R1/R2/R3/R4/R6） |
|---|---|---|
| 量的本体 | 同一次调用命中的行数 | 同一次调用命中的行数 × 每行成本 |
| 判据单位 | **行（与介质无关）** | **毫秒（与介质强相关）** |
| 当前读数 | 5,521 行（max） | 159.81ms（mean）/ 428.70ms（p99） |
| 谁在动它 | `NPROBE_WRITE_FINE=20` | `NPROBE_FINE=50` |
| **共同分母** | **每桶活行数（100.34）**、**每行 3KB** | 同左 |

⇒ **任何「只修一个」的方案都会在另一个上复现同一笔账**。
⇒ 因此本 ADR 的杠杆必须按「**动行数**」还是「**动每行成本**」来分类，而不是按「读/写」分类。

## §3 杠杆矩阵

> 每个杠杆都标：**只调参（可回滚）** / **改实现（改语义）**。
> 「乐观界 / 保守界」的**外推式子逐条写明**；无数据的写「未测」。

### L1 · 降 `ROUTER_NPROBE_WRITE_FINE`（20 → 7 或 8）

| 项 | 内容 |
|---|---|
| **类型** | **只调参（可回滚）** —— 改 `src/core/params.ts:128` 一行 |
| **机理** | 写入向量候选 = `nprobe × 每桶活行数`，线性于 `nprobe` |
| **收益（算式）** | 按 **max（H1 判定口径）** 线性外推：`5,521 × 7/20 = 1,932 行`（≤2,000 ⇒ **绿**）；按 **p99**：`5,297 × 7/20 = 1,854 行`；按 **mean**：`2,184.03 × 7/20 = 764.4 行`（`H2 = 0.0764%`）。取 8 则为 `5,521 × 8/20 = 2,208 行`（**仍红 1.10 倍**）⇒ **7 是唯一能过 max 的整数取值，8 不行**（⚠️推断） |
| **乐观界** | 桶组成的非线性使 max 不一定等比降；**若**降 `nprobe` 后命中桶更靠近质心（平均桶容更小）⇒ 实际可能优于 1,932。**乐观界 = 1,932 行以下** |
| **保守界** | **若** 7 个桶恰好落在 3 个最大的桶上 ⇒ 仍可能 >2,000。**保守界 = 无法从现有数据给出**（当前的 500 个样本**没有落盘「每次写入命中哪 20 个桶」**） |
| **代价** | **去重漏检率**：真重复若落在未被探到的桶 ⇒ 不合并。候选面从 2,184 → 764 行（−65%）⇒ 漏检面同比例扩大。**当前的量：未测**（没有「探针数 — 去重漏检率」对照曲线） |
| **是否改语义** | **否**（探针数是设计内旋钮） |
| **是否可回滚** | **参数可回滚（改回 20，一秒），但已产生的后果不可回滚** —— 见下 |
| **风险（★ 本条最重）** | **这是唯一「不可回滚」的调参项**：漏检的真重复在当次写入时就**各自落成两条独立记忆** ⇒ 参数改回 20 **不会**让它们重新合并。⇒ **风险不对称**：`NPROBE_FINE` 调错只是「召回结果变了」（可重算），`NPROBE_WRITE_FINE` 调错是**脏数据入库**（`DESIGN-v2-errata.md` 关于「老库越用越脏」的成因即此，`ivf.ts:440-442` 有逐字说明） |
| **耦合约束** | `params.ts:128` 注释「候选面 ≤ 召回路径」⇒ **写入探针必须 ≤ 召回探针**。若 L2 把 `NPROBE_FINE` 取到 10，则 L1 的 7 仍合法；若取 20，L1 可放宽到 7~20 |

### L2 · 降 `ROUTER_NPROBE_FINE`（50 → 10~20）

| 项 | 内容 |
|---|---|
| **类型** | **只调参（可回滚）** —— 改 `src/core/params.ts:125` 一行 |
| **机理** | 召回向量扫描 = `nprobe × 每桶活行数` |
| **收益（算式）** | 行数：`50→20` ⇒ `4,502.96 × 20/50 = 1,801.2 行`；`50→10` ⇒ `900.6 行`。<br>毫秒（**三点界**，单价全部有出处）：<br>· **热盘档**（`8~14 µs/行`，`DEVELOPMENT-PLAN.md:2293`）：`900.6 行 → 7.2~12.6ms`<br>· **当前档**（`35.491 µs/行`，D6）：`900.6 行 → 31.96ms`<br>· **冷盘档**（`212.025 µs/行`，同上出处）：`900.6 行 → 190.9ms` |
| **乐观界 / 保守界** | **乐观界** = 行数降 ⇒ 页缓存命中率升 ⇒ **单价反而降**（`900 行` 比 `4,503 行` 更容易全命中）⇒ 真实值**优于** 31.96ms，可能贴近 7~13ms。<br>**保守界** = 单价不变（35.491）⇒ **31.96ms**。⇒ **31.96ms 是保守界，不是乐观界**（这一点方向容易写反） |
| **代价** | **召回质量**。`DESIGN-v2-errata.md:2300` + ADR-33（`DESIGN-v2.md:6292`）：「**召回损失的唯一来源是探针数**，且可测（与 flat 全表扫对照，top-N 吻合率 ≥ 0.98）」。<br>⚠️ **引用精度**：`params.ts:124` 那句「召回损失的唯一来源」写的是 **`ROUTER_NPROBE_COARSE` 那一行**（粗层）；细层的同一性质由 `DESIGN-v2.md:3843`（`ROUTER_NPROBE_FINE` 行：「漏召更多；候选扫描量 = `nprobe_fine × 每桶成员数`」）+ ADR-33 的「**探针数**」（复数概念）承担 ⇒ **降 FINE 有据，但别引 124 那行**。<br>**损失量：未测**（无「探针数—top-N 吻合率」曲线；`DESIGN-v2.md:6292` 的目标是「吻合率 ≥ 0.98」，但那是**设计目标**而非当前实测） |
| **是否改语义** | **否** |
| **是否可回滚** | **完全可回滚** —— 召回是可重算的纯函数，改回 50 立即恢复 |
| **风险** | ① 若产品把 200ms 当 SLO，**外推拿不定**：把「old-path p99 + 向量扫描 p99」相加得 `78.62 + 428.70 × 20/50 = 250.1ms`（>200，红）；但同轮同批的实测显示这个加法本身会高估（`78.62 + 428.70 = 507.3` vs 实测 `370.12`，**高估 27%**）⇒ 修正后约 `182ms`（<200，绿）。⇒ **`nprobe=20` 对 200ms 是边缘，外推无法定论，必须重采**。`nprobe=10` 时区间为 `164~205ms`，同样边缘。<br>② 与 L1 的耦合（见 L1 末行） |

### L3 · 把向量按桶聚簇存放（物理上随 `fine_id` 连续）

| 项 | 内容 |
|---|---|
| **类型** | **改实现（改语义边界）** |
| **改哪里** | `schema/001_schema_v2.sql:329-335`（`vector_cell_members` DDL）；`src/vector/bucketAssign.ts:169-170`（唯一写入点）；`src/vector/ivf.ts:824 readMembers()` / `:844 readCandidateRows()` / `:462-470`（候选 SQL） |
| **★ 关键实现细节（不做这一条，L3 白做）** | **只给现有表加一列 `vector` 是无效的**：`vector_cell_members` 现在是**普通 rowid 表**，`PRIMARY KEY (fine_id, memory_id)` 落成一个**索引**，行体仍按**插入顺序**排在表 b-tree 里 ⇒ 加列后每行 3KB 的 blob 仍在**插入序**上 ⇒ **依然是散页读**。<br>⇒ 必须建成 **`WITHOUT ROWID` 表且 PK = `(fine_id, memory_id)`**（SQLite 的 `WITHOUT ROWID` 表按 PK 物理排序 ⇒ 同一桶的行**连续**），或建独立表 `vector_cells(fine_id, memory_id, vector) WITHOUT ROWID`。 |
| **收益（算式）** | **不降行数（H1/H2 一点不动）**。降的是「每行取回成本」：<br>· 数据量：`4,503 行 × (3,072 + ~24)B ≈ 13.9MB`，切成 **50 段 ≈ 280KB/段**的顺序读<br>· **乐观界**：13.9MB 顺序读 @1.5GB/s ≈ `9.3ms` + 每行解码 CPU（4,503 × 1~2µs = `4.5~9ms`）⇒ **≈ 15~20ms** ⇒ 相对 159.81ms 改善 **8~10 倍**<br>· **保守界**：页数只从「4,503 行 ÷ 约 2 行/页 ≈ 2,252 页」降到「13.9MB ÷ 8,192 = **1,697 页**」⇒ **页数仅降 1.33 倍** ⇒ 若收益**只**来自页数（假设随机惩罚完全不变）⇒ `159.81 ÷ 1.33 ≈ 120ms` ⇒ **改善 1.3 倍** |
| **收益区间诚实结论** | **1.3 ~ 10 倍，跨度 7.7 倍。** 收益主要来自「**随机 → 顺序**」，而非「页数变少」；而「随机惩罚占多少」在 `pageCacheState=unknown` 下**无法从现有数据拆出** ⇒ **不做实验无法定档**。这是 L3 唯一的诚实说法。 |
| **代价 · 三条边界冲突（必须逐条讲清，这是本节的重点）** | **① 会不会打破「`vector_cell_members` 唯一读取点、表名不外泄」？**<br>　**不会打破，但会改变它的分工**：`ivf.ts:822` 的边界是「**表名不得出本模块**」⇒ 把列加进同一张表，边界**原样成立**（`readCandidateRows()` 不再需要 JOIN `memories`，反而**少一个表名**）。<br>　**但**「本模块是唯一读取点」这句会变得**不完整**：`scanBucketCandidates()`（写入路径）也要读同一批列，而它在**同一个模块**里 ⇒ 仍成立。<br>　⇒ **真正被打破的是另一条**：`ivf.ts:683`「归属仍以库里的 `vector_cell_members` 为准」+ `bucketAssign.ts:10`「全库唯一写入点」⇒ 向量**从 `memories`（唯一真相）被复制到了桶表** ⇒ 出现**两个真相**。<br>**② 会不会与「`memories.embedding` 是唯一真相」冲突？**<br>　**会**，而且是**结构性的**：`memories.embedding` 是 §4.6 定义的派生值、`assignBucket/unassignBucket` 四条赋值路径都要维护它（`DEVELOPMENT-PLAN.md` 阶段 2 的硬断言）。把向量搬进桶表 ⇒ **双写一致性**成为新不变式（同一事务、同一归一化口径、同一维度校验），并且**桶表行与记忆行的生命周期必须严格同步**（`ON DELETE CASCADE` 已有，但「`embedding` 被置 NULL 而桶行未删」这种旧状态现在**能表达**，搬过去后**必须一并清理**）。<br>　**替代路线（成本更低，应优先评估）**：**不搬、只冗余** —— 桶表保留**一份副本**并把 `memories.embedding` 明确声明为**权威副本**，副本在**同一事务**内写、在**启动对账**（已有机制）时校验。⇒ 语义不变，但付 **+3GB 体积**（`1,000,000 × 3,072B = 3.0GB`）。<br>**③ 迁移与体积**<br>　· **体积**：+3.0GB 冗余（库当前量级：`memories` ≈ 3~4.5GB 向量 + 正文）。NVMe 1TB 有 860GB 可用 ⇒ **容量无压力**。<br>　· **迁移**：`vector_cell_members` 从 rowid 表改 `WITHOUT ROWID` **不能 `ALTER`**（SQLite 不支持）⇒ 必须「建新表 → 全量回填 → 改名」三步，且**回填 1,000,000 行 × 3KB = 3GB 写入**（参考 D14 灌库 425.5s 的量级 ⇒ **一次性 ≈ 5~10 分钟**⚠️推断）。<br>　· **迁移期内存**：峰值 RSS 已 11.77GB / 总 17.1GB（D13），回填若一次性 `SELECT ... JOIN` 物化会顶破 ⇒ **必须按 `fine_id` 分批**（每批 1 桶 ≈ 100 行 ≈ 300KB）。 |
| **是否改语义** | **是**（新增双真相 / 或至少新增一份必须对账的副本） |
| **是否可回滚** | **可回滚（但贵）**：保留旧 `memories.embedding` 读取分支即可退回（`readCandidateRows()` 改回原 SQL），迁移脚本可逆（删新表）。**前提：不要删 `memories.embedding`** |
| **风险** | **① 与行读计数器的交互 —— 会让 H1 看起来「真空通过」**（**必读**）：<br>　`bench/lib/harness.ts:977-988 classifyReadKind()` 按 **SQL 里出现的表名**分类：含 `memories` ⇒ `candidate`，含 `vector_cell_members` ⇒ `bucketMember`。<br>　L3 之后候选 SQL **不再 JOIN `memories`** ⇒ 它落到 `bucketMember` 类 ⇒ **`candidate` 计数变 0** ⇒ `bench/perf.ts:1177/1191` 的**真空通过兜底**会把 H1 判成「**真空通过（不合格）**」<br>　⇒ **结论：L3 单独上线会让 H1 从「红 2.76 倍」变成「真空通过红」，性质更糟（读数失去意义）**。⇒ L3 **必须**与「H1 的行定义」一起改（§5 ③）<br>**② 训练/重训联动**：桶表存副本后，**重训换桶必须同步搬运 3GB**（`bucketAssign` 的三步顺序不可颠倒） ⇒ 重训时长从 111.1 分钟（D14）进一步上升，**未测** |

### L4 · 两段式：量化码预筛 + 原向量重排

| 项 | 内容 |
|---|---|
| **类型** | **改实现（改语义：引入全库第二个近似来源）** |
| **改哪里** | 新增码表（如 `vector_codes WITHIN ROWID/…`）+ `src/vector/ivf.ts` 的 `search()` / `scanBucketCandidates()` + 重训管线的**重编码步骤** + **`bench/lib/harness.ts:977 classifyReadKind()`（必须同步改，见下）** |
| **机理** | 桶表里存 int8 / 二值 / PQ 码 ⇒ 先算近似分 ⇒ 只对过阈的 topN 取原向量精确重排 |
| **收益（算式）** | **同时降行数（部分）与字节数（大幅）**：<br>· **字节**：码表 int8 = `1,000,000 × 768B = 768MB`；二值 96B = `96MB`；PQ 64B = `64MB`（任务书给的三个量级一致）。单次扫描的字节：`4,503 × 96B = 432KB`（vs 现在 `13.8MB`）⇒ **字节降 32 倍**<br>· **毫秒**：码 `432KB` 顺序读 ≈ `0.3~1ms` + topN=64 原向量 `64 × 35.491µs = 2.27ms` ⇒ **≈ 3~4ms** ⇒ 相对 159.81ms 改善 **40~53 倍**（⚠️推断，假设码表按 `fine_id` 聚簇） |
| **★ 但「H1 达标」这件事，L4 只在一半情况下成立（本节最重要的更正）** | 分三种形态，**必须选一种并写进裁决**：<br>**(a) 码按「每码 1 行」存、且计数器不认新表**（默认结果）⇒ `classifyReadKind()` 对新表返回 `null` ⇒ **不计入 `candidate`** ⇒ H1 显示 `64 行` ⇒ **假绿**：绿的原因是**计数器看不见新读**，不是物理读变少。**这等于 §6 的「改判据让红变绿」，只是意外发生的。**<br>**(b) 码按「每码 1 行」存、且计数器扩展识别码表** ⇒ 写入侧 = `2,184.03 + 64 = 2,248.03 行` ⇒ **仍 > 2,000 ⇒ H1 仍红**（max 侧 `5,521 + 64 = 5,585` ⇒ 红 2.79 倍）。⇒ **L4 单独不能让 H1 达标**<br>**(c) 码按「每桶打包成 1 行（BLOB 数组）」⇒ 写入侧 = `20 + 64 = 84 行`、召回侧 = `50 + 64 = 114 行` ⇒ **真绿**（≤2,000，且逻辑上确实只读了 84 个行）**但「行」的含义已从『记忆行』变成『桶块』** ⇒ **必须重新声明 H1 的判据（§5 ③），否则读的人都以为「2,184 条记忆的候选只读了 84 行」** |
| **乐观界 / 保守界** | 毫秒：**乐观** = 码完全顺序 + 全命中 ⇒ ~3ms；**保守** = 码仍散页（未聚簇）⇒ `4,503 × 12~35µs = 54~158ms` ⇒ **L4 的收益完全取决于码表是否按桶聚簇 —— 与 L3 是同一件事** ⇒ **L4 应当与 L3 一起做，不是替换 L3** |
| **代价 · 四条** | ① **多一份码表**（768MB / 96MB / 64MB，按精度选）<br>② **重训要连带重编码**：重编码 `1,000,000 × 768` 次量化 ⇒ 时长**未测**；且**码表与新中心必须同批生效**（否则近似分与桶归属错配）<br>③ **近似分带来的「阈值边缘漏检」不可用精确断言证明**：阈值附近的候选（`DEDUP_COS_MIN` / `VECTOR_MIN_COS`）会因近似误差**漂移**，而**漂移方向不确定** ⇒ 无法写「不丢召回」的断言，只能写「吻合率 ≥ X」<br>④ **`DEDUP_COS_MIN` 边缘的判定漂移**：预筛用近似分淘汰的候选**不再进入精确重排** ⇒ 这在**去重路径**上等价于「静默提高了 `DEDUP_COS_MIN`」⇒ **与 L1 同类的脏数据风险，且更隐蔽**（L1 的漏检有 nprobe 可指，L4 的漏检在阈值边缘，**没有旋钮可回滚**） |
| **是否改语义** | **是**（打破 `DESIGN-v2.md:6292` ADR-33「桶内是全量精确点积」这条明文：`ivf.ts:640` 的「逐位一致」承诺**直接失效**） |
| **是否可回滚** | **可回滚（保留精确重排路径作为 fallback 开关）**，但**已因近似淘汰而未合并的重复不能回滚**（同 L1） |
| **风险** | 直接撞 ADR-33（「不引入 ANN」是已裁决的边界；两段式 = **引入了一个带损失的第一级**）⇒ **这一档不是性能问题，是设计契约问题**，必须先经裁决 |

### L5 · 重训时桶均衡（`ROUTER_BUCKET_MAX` 只是 P95 上限）

| 项 | 内容 |
|---|---|
| **类型** | **只调参 + 重训**（`ROUTER_BUCKET_MAX=300` → 更小的目标上限；k-means 加容量约束）⇒ **改参数、不改代码，但必须重训（111.1 分钟，D14）** |
| **机理** | 只压**尾部**（大桶），不动均值 |
| **收益（算式）** | 尾部证据：召回侧 `max 12,782` vs `mean 4,503` ⇒ `12,782 ÷ 50 = 255.6 行/桶`（最大桶）vs `90.06`（均值）⇒ **倾斜度 ≈ 2.84 倍**。<br>· 压到「最大桶 = 均值」⇒ `max → 50 × 90.06 = 4,503`、写入 `max → 20 × 109.2 = 2,184`<br>· **对 p99**：有效（p99 10,103 → 约 5,000~5,500）<br>· **对 mean**：**完全无效**（均值不动）<br>· **对 H1**：**仍红** —— `20 × 109.2 = 2,184 > 2,000`（见 §2.3）。要 H1 绿需**最大桶 ≤ 100 行**，即**比均值还小** ⇒ 桶均衡**做不到** |
| **乐观界 / 保守界** | 乐观 = 倾斜完全消除（`max = mean`）；保守 = 只能压 P95（`ROUTER_BUCKET_MAX` 现在是 300，实测最大桶 255.6 已经**低于**它 ⇒ **现在的参数根本没在约束它**） |
| **代价** | ① **重训 111.1 分钟/次**（D14）⇒ 反馈环 2 小时，**不能靠试错调**<br>② 若靠「增加细中心数」求均衡 ⇒ 见 L6 |
| **是否改语义** | 否 |
| **是否可回滚** | 可回滚（回训一次 111 分钟） |
| **风险** | **「调了 `ROUTER_BUCKET_MAX` 就宣布解决」是典型误判**（§6）：它只是 P95 上限，**实测 255.6 < 300 ⇒ 它现在一个桶都没触发** |

### L6 · 降桶粒度（`ROUTER_FINE_CENTERS` 10,000 → 20,000）· 补充杠杆

| 项 | 内容 |
|---|---|
| **类型** | **只调参，但触发重训** |
| **机理** | 平均桶容 `1,000,000 ÷ fine_centers` ⇒ 线性下降 ⇒ **行数直接下降**，且**不减少覆盖率**（结构上比 L2 更「像」免费） |
| **收益（算式）** | `fine_centers` 10,000→20,000 ⇒ 均桶 50.17 ⇒ 写入 `20 × 54.6 = 1,092 行`（**H1 绿**）、召回 `50 × 45.0 = 2,251 行`（约 −50%）。⚠️推断（假设新桶仍按均值分布、且 `nprobe` 不变） |
| **代价** | **召回覆盖体积同比例减半** ⇒ 召回损失**结构上等价于把 `nprobe` 减半**（`nprobe × 每桶体积` 才是覆盖量）⇒ **不是免费的**；且 **`route()` 的细中心点积数从约 1,000 升到约 2,000**（`200 粗 → 每粗下细中心`），路由成本 +约 1ms 量级 |
| **是否可回滚** | 可回滚，但**每次回滚 = 111.1 分钟重训** |
| **为什么列出来** | 因为它**是唯一「不动 nprobe 也能降行数」的纯参数手段**，而 nprobe 是**唯一被文档点名的质量闸门** ⇒ 对「不许降召回质量」的诉求，L6 比 L2 更**可辩护**（代价从「少探桶」变成「桶更细」，后者可量化成「覆盖体积」，前者只能量化成「损失」） |

### 4.4 ★ A 档是 B/C 的**前置验证**吗？—— 我的判断

**判断：`A 的调参` 不是前置（可跳过）；`A 的重采` 是前置（不可跳过）。这两件事必须拆开看。**

理由（三条，按权重）：
1. **B 的收益与 `nprobe` 无关**：L3 降的是「每行成本」，与探针数正交。⇒ 先降探针**不会**让 B 的收益更可测，反而**污染对照**（迁移前后的行数不同，无法判断「改善来自聚簇还是来自少探行」）。
2. **C 的收益上限要靠 B 的实测校准**，而**不**靠 A 的调参。C 的 `40~53 倍` 建立在「码表已按桶聚簇」上 ⇒ **C 的前置是 B，不是 A**。
3. **但 A 的「重采」是所有人共同的前置**：现在 `pageCacheState=unknown` ⇒ **所有毫秒数不可比**（`pageCacheState.note` 逐字写了这条）。没有 warm/cold 两档基线，B/C 的收益**无法归因到任何因子**。
   ⇒ 而这个重采**不需要改任何参数**（只加 `--cache-state=warm|cold`）⇒ **可以把它从 A 里拆出来，单独当作 0.5 轮的动作**，这样 B/C 就不必先付质量代价。

⇒ **可执行建议**：**先跑「零调参重采」（0.5 轮）→ 再决定 A 还是 C。**
⇒ **不推荐 B 单独作为终点**：B 不能解决硬门槛 H1（它不降行数），只能改善**参考线**（R1/R2/R3）。
   ⇒ 若目标是「H1 变绿」，B 单独无意义；若目标是「接线后 R3 不破线」，B 有意义且**不降质量**（这是 B 的真正价值定位）。

## §5 建议 + 待裁决项

### 5.1 建议

**建议：先做「零调参重采」（0.5 轮），然后按「能否接受未测的去重漏检率」二选一：能接受 ⇒ A 档止血；不能接受 ⇒ 直接排 C 档，跳过 A/B 的参数下调。**

理由（每条都指回数字）：
1. **H1 是唯一真门槛，且结构性不可达**（§2.3：`2,000 ÷ 20 = 100 < 100.34`）⇒ 不选 L1/L4 就没有第三条路。**「再优化一下」不会有结果。**
2. **A 档便宜到没有理由不做，但它买的是「绿」而不是「对」**：`1 轮` vs `C 的 5 轮 + 每轮 111 分钟重训`。
   但 A 的代价是**唯一不可回滚的**（脏数据）⇒ **在有质量曲线之前，A 只能当「止血」，不能当「方案」**。
3. **C 档能同时满足「H1 绿」与「质量不降」，但它的前提不是预算，是一个裁决**：`H1 的「行」是什么`（§5.2 ③）。
   **不先裁这一条就开工，最可能的结局是「实现了、判据不认」或「判据绿了但绿的理由是计数器看不见新表」（附录 B）** —— 后者比现在更危险。
4. **B 档单独不该被选**（不解决 H1），但**如果你真正担心的不是 H1 而是「接线后召回破 200ms」**，那么 **B 才是对症的那一档**（它不降质量，且是唯一能让 R3 绿的路线）。⇒ **选哪档取决于「本轮要交的是 H1 还是 R3」——这个问题现在没有答案，正是待裁决①。**

### 8.2 结论：**A 档永久出局；C 档升级为 C′（可证零漏检），且 C′ 不再破 ADR-33**

**② = (a) 这一条就把 A 档杀死了**：`ROUTER_NPROBE_WRITE_FINE 20 → 7` 的唯一收益来自「少探桶」，
而少探桶的**定义**就是「少看一批候选」⇒ **必然产生漏检**（L1 的「不可逆点」一栏原文）。
⇒ **L1 从候选集里删除**。连带地，**L6（降桶粒度）也不行** —— 它的召回损失「结构上等价于把 `nprobe` 减半」（§3 L6 原文）。

**更重要的连带后果：ADR 原文 L4 的「近似分淘汰」形态也出局了。**
L4 原文的代价 ③④ 说的是「近似误差导致阈值边缘漂移，**漂移方向不确定**」⇒
那正是**漏检**，与 ②(a) 直接冲突。

⇒ 但这不是死路：**把 L4 从「近似淘汰」换成「可证上界剪枝（admissible pruning）」，就能同时满足
「零漏检」与「几十倍收益」**，而且——

★ **它不再破 ADR-33**（这条要改原文的结论）：
ADR-33（`DESIGN-v2.md:6292`）的实质是「**桶内是全量精确点积**、结果与 flat 全表扫一致」。
可证上界剪枝**不改变结果集**（下面 8.3 给了证明），它跳过的每一行都能**证明**「不可能入选」⇒
它是一次**索引式优化**，不是「引入带损失的第一级」⇒ **ADR-33 不需要被推翻，只需要加一条勘误说明「桶内精确性由剪枝的可证性承担，而不是由『扫完整个桶』承担」**。

### 8.3 零漏检的证明（这是 ②(a) 能被满足的全部依据）

记查询为 `q`（已 L2 归一化 ⇒ `‖q‖ = 1`），候选记忆的原向量为 `x`（写入时已 L2 归一化 ⇒ `‖x‖ = 1`），
其 int8 码还原值为 `x̂`，编码期算出并落库的误差为 `ε = ‖x − x̂‖₂`。则

```
真实余弦  cos_true = q·x
                  = q·x̂ + q·(x − x̂)
                  ≤ q·x̂ + ‖q‖·‖x − x̂‖        （Cauchy–Schwarz）
                  = q·x̂ + ε  =:  upper        （‖q‖ = 1）
```

⇒ **`upper` 是 `cos_true` 的上界，且上界本身可由码算出**（`q·x̂ = scale × Σ q_j·int8_j`，`ε` 落库）。

- **写路径（阈值语义）**：`cos ≥ DEDUP_COS_MIN` 才进候选 ⇒
  **只跳过 `upper < DEDUP_COS_MIN` 的行** ⇒ 被跳过者的 `cos_true ≤ upper < 阈值` ⇒
  **它本来也不会进候选** ⇒ **结果集与全量精确扫描逐位相同**。
- **读路径（top-K 语义）**：不要阈值。按 `upper` **降序**做精确重排，维护 top-K 的小顶堆；
  当「剩余行的 `upper` 最大值 `< 堆内第 K 名的精确分`」时停止 ⇒ 剩余行**全部**不可能进入 top-K ⇒
  **返回的 K 条与全量精确扫描逐位相同**。
  ⚠️ **停止条件必须用严格小于**（`<`），用 `≤` 会把「`upper` 恰好等于第 K 名」的行错误跳过 ⇒ 同分时的 `id 升序` 定序会漏（`dedupCandidates.ts:332-341` / `ivf.ts` 的 `compareHits` 都对定序敏感）。

⚠️ **这条证明成立的前提有三个，缺一个就退回「有漏检」**：
① `‖q‖ = 1`（由 `normalizeQueryEmbedding()` 保证，`recall.ts:939`）；
② `‖x‖ = 1`（由写入侧 L2 归一化保证）；
③ `ε` 是**真误差**（编码时逐行实算，不是 `scale·√d/2` 那种估算上界）。
⇒ 验收断言 A3（见规格 §6）就是专门钉第 ③ 条的。

### 8.4 四条连带后果（必须与裁决同批读）

1. **① （召回 SLO）未裁不阻塞**：C′ 的目标读数就是 `3~15ms` 量级（远低于 200ms），
   SLO 定 200 / 300 / 不设，**三种答案下 C′ 都合格** ⇒ 可以后补。
2. **⑥ 事实上已被强制为 (a)「允许红着交」**：②(a) 之后只剩 C′ 一条路，而 C′ 是 **5~6 轮**（规格 §5）。
   ⇒ 「不允许红着交」= 要求在一轮内做完 5 轮 ⇒ **不是排期问题，是无解**。
   ⇒ 若 ⑥ 真要选 (b)，唯一出路是**推翻 ②**。**这一条请明确确认**。
3. **ADR 原文 C 档的形态 (c)（「码按桶打包成 1 行」）有一个原文没查的缺陷 ⇒ 改用形态 (b′)**：
   打包成 1 行 ⇒ 每次 insert 都要**重写整块**（`109 行 × 768B ≈ 84KB`）⇒
   **写放大从「读」转移到「写」**，而写入路径本来就是被考核方 ⇒ **得不偿失**。
   ⇒ 采用 **「每码 1 行、但按 `fine_id` 聚簇存放」（新增 `vector_codes` 表，`WITHOUT ROWID`，`PK(fine_id, memory_id)`）**：
   insert 只追加 `768B`、读按桶连续 ⇒ 两种放大都小。
   ⇒ 于是 H1 的「行」确实需要重声明 —— **但重声明的落点不是「码行数」，是「字节数」**（见 8.5）。
4. **④ 维持 max，且这不是「不改」而是「不敢改」**：按 max 需探针 ≤7、按 mean 只需 ≤18
   （§5.2 ④ 原文）⇒ 换成 mean 等于**把门槛放宽 2.6 倍**，且属 §6 P2。
   ⇒ 但在 C′ 下这条**已经无关紧要**：字节口径下 max 也在预算内（8.5）。
5. **⑤ 与本轮施工无关**：C′ 会让 R1/R3 天然变绿（`3~15ms` vs 20ms / 200ms 线），
   R5（5ms）仍受 `otherMeanMs = 9.86ms` 下限约束、**任何档都红**（§6 P7）。
   ⇒ ⑤ 的归口可以留到 C′ 落地后再做，**不阻塞开工**。

### 8.5 ★ H1 的重新声明（③ = 允许 的**具体形态**，施工前必须钉死这一条）

**新判据：`H1′ = 单次写入去重从向量存储读出的字节数`，门槛 `≤ 6,144,000 B`。**

为什么是字节而不是「码行数」（三条理由，按权重）：

| # | 理由 |
|---|---|
| 1 | **它保住原预算的含义**：`2,000 行 × 3,072 B（768 维 float32）= 6,144,000 B` ⇒ 原门槛真正约束的是**每次写入搬运多少向量字节**（`3 KB/行` 这个换算写在 `schema/001_schema_v2.sql:16` 的页大小注释里）。行数只是那个年代的计量单位。 |
| 2 | **它与实现无关**：码 768B / 码 96B / 打包块 / PQ —— 任何实现都按「实际搬运字节」判，**不会出现「换了存储形态就换了一把尺子」**。而「码行数」这个口径对「打包形态」和「每行形态」给出**完全不同**的数 ⇒ 它是个**实现相关**的判据，比行数更糟。 |
| 3 | **它是升级不是降级**（§6 P2 的红线）：行数 × 3,072B 本身**假设了每行固定 3KB**；字节口径**不假设任何行长**。⇒ 对原本那批读 3KB 行的实现，**两者逐位等价**（`N 行 ⇔ 3072N 字节`）；对新实现，字节口径给的是**更准**的数。 |

**双读数并列（防「绿得没道理」）**：bench 必须**同时**落盘并打印
`memoryRowsRead`（原口径）/ `codeRowsRead` / `bytesRead`（新判据）/ `candidateUniverse`（命中桶内的候选总数，**不变**）。
⚠️ **判定只看 `bytesRead`**，但三个数并列 ⇒ 谁都能一眼看出「省下的是字节还是候选」。

**H2′ 同步**：`bytesRead ÷ (库规模 × 3,072 B) ≤ 0.2%`（= 原来的 `行数 ÷ 库规模`）⇒ 1M 时两条门槛**同一个数**。

### 8.6 预估读数（⚠️全部推断，施工后必须重采）

| 量 | C′ 预估 | 算式 |
|---|---|---|
| 写入 `bytesRead`（mean） | **≈ 1.72 MB** | `2,184 × 768B = 1.68MB` + `64 × 3,072B = 0.20MB` |
| 写入 `bytesRead`（max） | **≈ 4.44 MB** | `5,521 × 768B = 4.24MB` + `0.20MB` |
| **H1′ 判定** | **≈ 4.44MB / 6.14MB = 0.72 ⇒ ✅ 绿（余量 28%）** | ⚠️ **余量不宽**（`0.72` 不是 `0.1`）⇒ 必须重采确认，不许拿它当承诺 |
| 召回 `bytesRead` | **≈ 3.66 MB** | `4,503 × 768B = 3.46MB` + `0.20MB` |
| 召回延迟 | **≈ 11~20 ms**（不是 40~53 倍） | 码 IO `4.24MB/1.5GB·s⁻¹ ≈ 2.8ms` + 码点积 `5,521 × 768 ≈ 4.2M` 次 MAC ⚠️**未测**（若按 200~400 M MAC/s ⇒ `10~21ms`）⇒ **瓶颈从 IO 转到算力** |
| 存储增量 | **+768 MB**（1M 行）+ 每行 `ε`/`scale` 8B ⇒ +8MB | `1,000,000 × 768B` |

⚠️ **三条要改原文预期的地方**（因为本节的估法与 §3 L4 不同）：
- §3 L4 的「40~53 倍」建立在**二值 96B 码**上；**int8（768B）只到约 8~14 倍**，且瓶颈换成 CPU。
  ⇒ 若要求更高倍数，需要 PQ/二值码，但**码越窄 ⇒ `ε` 越大 ⇒ 剪枝率越差** ⇒ 必须实测这条曲线才能选码宽。
- §3 L4 的「H1 只有形态 (c) 能绿」**作废**：形态 (b′) + 字节口径同样能绿，且没有写放大缺陷。
- §3 L4 的代价 ③④（阈值边缘漂移、不可回滚）**作废**：可证剪枝的漂移为 0。

## 附录 A · 与任务书口径的三处差异（读本文档前必须知道）

> 这三条**不是「任务书写错了」**，而是**仓库里存在两个时点的口径**。本 ADR 一律以**当前 HEAD** 为准，并把差异写明，避免下一手引用到过期的那一份。

### A-1 · `78.62ms` 是 R4（不含向量路），不是「错标的门槛」
`DEVELOPMENT-PLAN.md:2296` 把 **R4 = recall P99（不含向量路 · 现状口径）≤ 200ms** 列为**参考线**并判「达标」。
它测的就是「文本路 + 图谱路」，**本身没有造假**。风险在**转述**（§1.3 / P3）。
⇒ 本 ADR 的表述：**R4 = 78.62ms ✅（已达标，口径正确）；R3（含向量路）= 未测；bench 强制档 p99 = 370.12ms。**

### A-2 · 那份 JSON 的 `failures` 数组用的是 **8da0817 之前**的 H1 判据
`perf-1000000-vector-wired-nvme.json: failures` 里写的是
「候选读取行数（H1）**12,782 行** > 2000」（= 召回探针 20/50 的 `candidateReadRows`）。
但 HEAD（`8da0817 fix(bench): H1/H2 判定按归口指向写入路径`）之后，**H1 的唯一判据量是 `writeSegments.vectorCandidateRows.max` = 5,521 行**。
⇒ **同一份 JSON，用 HEAD 的判据读，结论仍是红（2.76 倍），但数从 12,782 变成 5,521。**
⇒ 「6.39 倍」与「2.76 倍」是**两个不同的量各自有数**，不是一个数在改善（`DESIGN-v2-errata.md:2316-2317` 已写死这条防误读语：「6.39 倍没有变小，它换了主语」）。

### A-3 · 毫秒类四条：`bench` 判它们，计划稿说它们是参考线
`bench/perf.ts` 的 `THRESHOLDS` 仍把 `recallP99Ms / writeP99Ms / vectorRouteP99Ms / vectorRouteShare` 参与 `checkPerf()` 并写进 `failures`；
而 `DEVELOPMENT-PLAN.md:2293-2297` 已把它们定为 **R1~R5 参考线（不判 P2 收官）**。
⇒ **同一份 JSON 会出两种结论**：`failures` 说 4 条红，计划稿说「参考线不判」。
⇒ 这是 §5 待裁决⑤ 的事实基础。**本 ADR 只用 H1/H2 下「达标/不达标」结论，其余一律称「观测值」。**

## 附录 B · 为什么「L3/L4 会让 H1 变绿」这句话必须加三个限定词

| 形态 | `candidate` 计数会变成 | H1 判定 | 这个「绿」可信吗 |
|---|---|---|---|
| 现状（读 `memories`） | 5,521 | 红 2.76 倍 | — |
| L3（读桶表，不 JOIN `memories`） | **0**（落到 `bucketMember` 类） | **真空通过 ⇒ 不合格** | 不可信：**读数失去意义**，靠 `perf.ts:1177/1191` 兜底抓住 |
| L4(b) 每码 1 行 + 计数器认新表 | `2,184 + 64 = 2,248` | **仍红 1.12 倍** | 可信（确实读了 2,248 行） |
| L4(b) 每码 1 行 + 计数器**不**认新表 | `64` | 绿 | **不可信：假绿**（物理读没少，只是计数器瞎了） |
| L4(c) 码按桶打包（每桶 1 行） | `20 + 64 = 84` | 绿 4.2% | **可信，但「行」的含义已变** ⇒ 必须先裁决 §5 ③ |

⇒ **一句话**：**「降了行数」和「判据认了」是两件事；只有「物理读的行真的少了」且「计数器看得见它」同时成立，绿色才有意义。**
