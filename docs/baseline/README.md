> ⚠️ **百万级的三个脚本共用同一份库**（`--db=... --reuse=true`）：
> 「灌库 + 训练」在百万级要 ~5 小时 ⇒ 三个脚本各跑一次 = 15 小时，不可接受；
> 而且**三个脚本必须测同一份语料与同一套分桶**才有可比性 ⇒ **一次准备、三次测量**。
> ⇒ **`--reuse=true` 是必须的**，且它**依赖库旁的 `*.manifest.json` 清单**（记录种子与规模）
> ⇒ **清单丢了 ⇒ 下一次跑会删库重灌（5 小时）** ⇒ 复用期间**不要删那份清单**。

> ⚠️ ★ **P99 的样本量下限（2026-11-01 补）**：`bench/perf.ts` 的 `--queries` / `--writes`
> **必须 ≥ 100**（nearest-rank 口径下，**n < 100 时 P99 就是最大值** ⇒ 那个数不是 P99，
> 是「最大的一次」）⇒ **样本量不足 ⇒ 该 P99 不可判定**（既不算达标、也不算不达标）。
> ⇒ **`perf-*.json` 用 `--queries=200 --writes=200`**（P99 至少要有 100 个样本才可判定）。
> ⇒ ⚠️ **旧数据（`--queries=50` / `--writes=50`）的 P99 不可判定** ⇒ 已按新口径重刷。
>
> ⚠️ **为什么 `agreement` / `baseline-flat` 在百万级用小样本**（**它们不是 P99**）：
> · `agreement` 的判据是**逐查询的精确断言**（错数 = 0 / 越界数 = 0 / 桶内逐位相同）
>   ⇒ **不是统计量** ⇒ 10 条查询就足以判定「对不对」；
>   （吻合率那个比例是统计量 ⇒ 它的采样精度受查询数限制 ⇒ **读它时要连 `queryCount` 一起读**。）
> · `baseline-flat` 的**每次查询 = 一次全表精确扫描**（百万级 ≈ 15 分钟/次）⇒ 查询数直接乘在成本上
>   ⇒ **2 条**是「跑得完」与「有代表性」之间的取舍 ⇒ **它是「证据」不是「验收条件」**（见计划稿原文）。

## 怎么读这些数字

### 1. `phases`（相位耗时与峰值内存）

| 字段 | 含义 | 口径 |
|------|------|------|
| `loadMs` | 灌库耗时 | 100 万条 ≈ 3.2GB 的 BLOB 写入 |
| `trainMs` | 训练耗时 | **生产重训序列**（`src/vector/rebuild.ts` 的 `rebuildBuckets`） |
| `rssBeforeTrainBytes` | 训练**前**的 RSS | 与峰值对比 ⇒ 训练自身的增量 |
| `peakRssBytes` | **进程高水位** RSS | ⚠️ **含灌库阶段的占用** ⇒ 是「训练期峰值内存」的**上界**，不是纯训练峰值 |

### 2. `machine`（机器环境）

⚠️ **P99 是「这份数据 + 这台机器」的结论** ⇒ 没有机器信息的 P99 不可复现、不可比较。
⚠️ ★ **但 `machine` 块不能整体当「机器指纹」用**（2026-11-01 订正）：
`freeMemoryBytes` / `usedMemoryBytes` 是**采集瞬间的快照**（`freemem()`）⇒ **每次运行必然不同**
⇒ **不能**据「两个 JSON 的 `machine` 不完全相同」就断言「不是同一台机器 / 两个 P99 不可比」。
⇒ **可比性看硬件标识**：`platform` / `node` / `cpuModel` / `cpuCount` / `totalMemoryBytes`
（＋ `benchNow` / 语料规模）⇒ **这几项相同 ⇒ P99 可比**。

### 3. 百分位

**nearest-rank**：`rank = ceil(p/100 × n)`（1 起数），样本升序。
`n = 0` ⇒ 返回 `0`（不是 `NaN`）。
⚠️ ★ **样本量下限（可判定性的前提）**：**n < 100 时 P99 落在最大值附近** ⇒ 那个数**不是 P99**，
是「最大的一次」⇒ **不可判定**（既不算达标、也不算不达标）。
⇒ 落盘数据的 `count` 字段**必须 ≥ 100** 才允许拿它的 P99 下结论。

### 4. 预热

`warmupRounds = 20` 轮**不计入统计**（recall / 向量路 / **写入**都预热）。
⚠️ **写入也必须预热**：第一次写入会承担「WAL 首次落盘 + 页缓存装载 + 中心向量缓存建好」
的一次性成本 ⇒ 不预热 ⇒ **P99 = max = 第一次写入**（实测 10k 规模：首次 245ms、后续 ~4ms）。
⚠️ ★ **但预热只解决「第一次」，解决不了「周期性停顿」**（2026-11-01 实测）：
1 万条 / 200 次写入的**逐样本**分布里，**离群样本是周期性出现的**（#2/#3、#52/#53、#98/#99、
#147/#148、#196/#197 ⇒ 约每 49 次一轮），单次可达 **0.8~1.3 秒**，而其余样本 p50 ≈ 6.8ms。
⇒ ⇒ **写入 P99 天然被周期性事件支配**（WAL checkpoint / FTS5 段合并一类），
**不是**「某一次写慢了」⇒ **预热再多轮也不能把它压下去** ⇒ 读写入 P99 时**必须先看分布**（p50/p90/p95），
不能只看 P99。

## 三条「口径」的读法

### 吻合率

- **分母** = flat 全表扫描的 **top-20 全集**（`|flat_top20|`）
- **分子** = `|bucket_top20 ∩ flat_top20|`（**集合交集**，不是顺序比较）
- **判据** = 总体 `≥ 0.98`（**软阈值** ⇒ 允许「漏」）
- ⚠️ **不查条数相等**（探针边界效应 ⇒ 允许少一条）

### 「只漏不错」

| 断言 | 分母 | 允许吗 |
|------|------|--------|
| 分桶 top-20 ⊆ flat top-20（**不错**） | flat 的 **top-20** | **错数必须为 0** |
| 分桶候选 ⊆ flat **候选全集**（C29） | flat 的**候选全集**（不是 top-20） | **越界数必须为 0** |

⚠️ **为什么是两条**：前者比的是**结果**，后者比的是**候选面**（桶扫过的那批行）。
用 top-20 当后者的分母 ⇒ 探针不足会被误判成算法错误（**假失败**）。

### 前置测量（`baseline-flat`）

- **分子** = flat 路线下的向量路耗时（全表精确点积，**流式**扫描）
- **分母** = 分子 + `MemoryStore.recall()`（文本路 + 图谱路）
- ⚠️ **它与 `perf.ts` 的 `vectorRouteShare` 是两条不同的数**：
  本脚本是**改造前**（预期 **≥80%**），`perf.ts` 是**改造后**（门槛 **≤20%**）
  ⇒ **方向相反、绝对值不同** ⇒ 不许混用。

## ⚠️ 这个基线**能测**什么、**不能测**什么

**能测**（且是本任务的正题）：

- 分桶几何：探针覆盖、桶大小分布、扫描量、点积次数
- P99 延迟（recall / 写入 / 向量路）与**向量路在一次召回里的占比**
- 训练期峰值内存（**资源规划**用）
- **探针边界造成的漏召**（吻合率）与「只漏不错」这条硬性质

**不能测**（**别拿它当真实模型的结论**）：

- 真实 embedding 模型的**语义质量**（本基线的「同义」是**人工构造**的）
- 真实中文长文本的**分布漂移**、**跨语言**
- 真实模型在 `DEDUP_COS_MIN`（0.92）附近的**真实判定分布**
- **真实召回质量**（本基线不评估「召回来的对不对」，只评估「分桶与全表扫描差多少」）

⇒ **所有结论只在「本语料 + 本 embedder + 本机器」这个域内成立。**

---

## 三个问题的答案

### ① 合成的 embedder 怎么让「同义改写」真的接近？

**构造出来的，不是碰巧的。** `bench/embedder.ts` 的每个词都有一个**层级方向向量**：

```
dir(word) = normalize( 0.78·v_group + 0.30·v_sub + 0.12·v_comm + 0.25·v_lex )
vec(doc)  = normalize( Σ_{word ∈ doc} dir(word) )
```

- `v_group` 是**同义组共享的方向** ⇒ **同组的不同词彼此就是「同义改写」**
  ⇒ 换词不改义 ⇒ 夹角很小。
- `v_lex` 是**词汇噪声**（词级哈希到 4096 个槽）⇒ 不同的词之间有弱随机偏移。
- 跨组的方向近乎正交（768 维）⇒ 语义距离清晰。

**实测（不是论证）**：

| 量 | 实测 | 出处 |
|----|------|------|
| 同组两个**词**的余弦 | **0.92** | `runEmbedderSelfCheck().synonymCosine` |
| 跨组两个**词**的余弦 | **0.087** | `runEmbedderSelfCheck().unrelatedCosine` |
| **同义改写**（查询 vs 它改写的那条记录）的余弦 | **0.97**（1 万条实测，均/小/大 = 0.9721 / 0.9694 / 0.9742） | `agreement-*.json` 的 `synonymCosineMean/Min/Max` |
| 同义改写余弦的**硬下限** | 0.5（不满足 ⇒ 吻合率结论无效 ⇒ 判红） | `SYNONYM_COSINE_MIN` |

⚠️ **查询是「真改写」**：查询正文**不是**库里那条记录的原文
（那会变成「自己召回自己」）⇒ 而是把它的 3 个词**各换成同组的另一个词**
⇒ 表面不同、语义同组 ⇒ 余弦 0.97 ⇒ **「同义改写在向量上真的接近」有了实测数字**。

### ② 吻合率的断言怎么写成「只漏不错」？

拆成**两条独立断言**（C30 的分区）：

| 区 | 断言 | 分母 | 允许吗 |
|----|------|------|--------|
| **不错**（算错） | 分桶 top-20 ⊆ flat top-20 ⇒ **错数 = 0** | flat 的 **top-20** | **一条都不许多** |
| **不错**（候选面，C29） | 分桶候选 ⊆ flat **候选全集** ⇒ **越界数 = 0** | flat 的**候选全集** | **一条都不许越界** |
| **只漏** | `|intersect| / |flat_top20| ≥ 0.98` | flat 的 **top-20 全集** | **允许漏**（比例被 0.98 卡住） |

- 「漏」= flat top-20 里有、分桶 top-20 里没有的 ⇒ **允许** ⇒ 只体现在吻合率上。
- 「错」= 分桶 top-20 里有、flat top-20 里没有的 ⇒ **不允许** ⇒ 就是集合包含断言。
- ⚠️ **不查条数相等**（探针边界效应 ⇒ 允许少一条）。
- ⚠️ **集合交集，不是顺序比较** ⇒ 探针命中顺序不同不算「错」。
- ★ 另外还有**第三条硬断言**（C30 的「算错」那半）：
  **桶内 top-K == 对同一个桶集合做全量精确扫描的 top-K（逐位相同）**
  ⇒ 证明「桶内是精确点积，不产生近似误差」。

### ③ bench 怎么与 `pnpm run verify` 解耦？

| | 重测 | 守门 |
|---|------|------|
| 在哪 | `pnpm exec tsx bench/*.ts` | `tests/bench/bench-smoke.test.ts`（**在 verify 链里**） |
| 规模 | 100 万条 | 1500 条 |
| 耗时 | 几分钟~小时 | **~5 秒** |
| 断言什么 | 全部口径 + 数字 | **同一套断言逻辑**（不含性能达标） |

- ⚠️ **为什么重测不能进门禁**：百万级一次要 ~2 小时 ⇒ 每次 CI 都跑一遍 ⇒
  门禁从「秒级」变成「小时级」；而且 **CI 机器的性能不代表**性能基线的结论
  （基线必须在**记录在案的**机器上采）。
- ⇒ **重测靠人跑脚本，守门靠小规模冒烟**。
- ⚠️ **门禁里只断言「逻辑正确」，不断言「性能达标」**：性能门槛**按归口分两档**
  （★ 2026-11-01 架构裁决，详见 `docs/design/DEVELOPMENT-PLAN.md` 的 P2-T08 门槛表与
  `docs/design/DESIGN-v2.md` §12 阶段 2 的验收清单）：
  - **硬门槛（归 P2，不达标 = 分桶架构不成立）**：**向量路 P99 ≤ 20ms**、**向量路占总耗时 ≤ 20%**
    ⇒ 量的是**分桶后向量路自己**的成本。
  - **参考线（归文本路，不判 P2 收官）**：**recall P99 ≤ 200ms**、**写入 P99 ≤ 5ms**
    ⇒ 量的是**整条流水线**（文本路 FTS5 + 图谱路 + 写入的索引维护）；**P2 既没造它、也没改它**
    ⇒ 仍然**必须测、必须落盘、必须给出归因**（是文本路？索引维护？规模效应？）。
  ⇒ **两档都放不进门禁**（共享机器上必然 flaky）⇒ 门禁只断
  「吻合率口径 / 只漏不错 / 桶内精确性 / 语料可复现 / embedder 确定性 / P99 工具自检」。
- ⚠️ ★ **100 万条上 recall / 写入那两条参考线当前不达标**（旧数据：recall P99 678ms、写入 P99 658ms）
  ⇒ 这是一个**归文本路的待办欠账**（见 `docs/progress/stage2-progress.md`），
  **不是** P2 的失败；但也**不得**据此宣称「整条流水线性能达标」。
- ⚠️ **构建产物不含 bench**：`tsconfig.json` 的 `include` 含 `bench`（**类型检查覆盖它**），
  但 `tsconfig.build.json` 的 `include` 只有 `src` ⇒ `pnpm run build` 不产出 bench。
