### 设计怎么说

- `DESIGN-v2.md:2161-2183`（§4.9 步骤 3a2 的两层架构说明块）明确：
  - 实时层（分桶近似）**本版已实现**；
  - 宿主调度层：「由**调用方在自己的进程/线程里**周期性做**分片 flat 全量近重复扫描**」；
  - 「⚠️ **库内没有定时器、没有后台线程**（ADR-5 全同步）：这段扫描**不是库的能力**，库只提供同步的写方法；**调度归宿主**」；
  - 「**本版取后者**：宿主在扫描时携带原始文本，**走同一条 3c 路径**」。
- `DEVELOPMENT-PLAN.md:1988-1994`（P2-T07 软阈值）把它写成**已知代价，不是缺陷**：
  「实时层命中率 ≈ 40%…漏检 ≈ 60% ⇒ 由宿主调度层补齐（**这是已知代价，不是缺陷**）」。
- §14.3 边界原则 1：「每个承诺都要能指到**唯一**代码路径」；`src/index.ts` 文件头把导出面定义为
  「**本文件是「公开承诺」的清单**：导出的每一个名字都要能指到唯一代码路径」。

### 结论

**① 明确结论：❗ 不阻塞 P2 收官**（代码层面**无缺陷**），**但需要架构师补一份设计**（严重级 **Major · 设计缺口 · 路由 = software-architect**）。

理由链：

1. `mergeMemory()` **不是 §6 的 23 个公开方法之一**，§3.1 的方法归位表把它归到**任何阶段都没有**。
   ⇒ **在 P2 的导出面里加它，等于把 §3.1 的「行级小计之和必须等于 23」变成 24**，
   **越过了 §3.1 与 §12 的方法覆盖表** ⇒ 这不是工程师能自行决定的事。
2. P2-T07 的**硬断言清单（5 条）里没有一条**要求「宿主能通过公开 API 触发第二层合并」。
   ⇒ 按任务边界验收，**P2-T07 是完整的**。
3. 设计自己把宿主调度层划在**库的能力之外**（「调度归宿主」），
   并把「实时层漏掉的近重复会在库里停留一段时间」写成**明写的已知代价**。
4. ⇒ **正确处置**：**不改导出面**（本次 QA 也**没有**改），
   由架构师在**阶段 4/5 之前**补一份设计（可选形态：① 给 `mergeMemory` 一个 §6 位置的正式方法；
   ② 或定义一个「宿主扫描 → 标记 → 提示」的**协议**而不新增方法；
   ③ 或把它整体划到阶段 5 的 `verifyIntegrity` 旁路）。

### ⚠️ 但必须被记录的真实缺口

设计说宿主「携带原始文本，走同一条 3c 路径」，而 **3c 是 `write()` 内部的合并分支**。
宿主拿到「某条记忆 id + 原始文本」之后，**用现有的公开 API 无法表达「把它与这条合并」**：

- `write()` 会**自己**重新收集候选（走的是分桶近似）⇒ **恰好复现漏检的那个探针边界**，
  ⇒ **用 `write()` 走不通**；
- `updateContent()`（阶段 4）语义是「绕过去重直接改写」⇒ **不是合并**；
- `mergeEntities()` 是**实体**合并 ⇒ 不是记忆合并。

⇒ **§4.9 步骤 3a2 的第二层目前对宿主不可实现**。这不是「实现漏了」，是**设计缺口**
⇒ 必须在阶段 4 接向量路之前由架构师补上，否则 §4.9 的两层架构只有一层能落地。

### 「半承诺」核查：`CoactPair` / `CoactSkipped` / `MergeEventPayload3c`

| 检查项 | `MergeEventPayload3c` | `CoactPair` / `CoactSkipped` |
|---|---|---|
| 导出形式 | `export { … type MergeEventPayload3c }` | `export { … type CoactPair, type CoactSkipped }` |
| **运行时是否存在** | ❌ **不存在**（`dist/index.js` 里 **0 次命中** ⇒ tsup 已擦除） | ❌ **不存在**（同上） |
| 生产代码是否在用 | ✅ **在用**：`src/store/merge.ts:369` 构造该 payload | ❌ 仅在 `src/core/events.types.ts` 里声明 |
| 属于哪个阶段的能力 | **P2**（§4.9 步骤 3c 的 `merge` 事件 payload） | **P3**（coacts 是阶段 3 的产物） |
| 是谁的类型字段 | — | **`TouchEventPayload` 的可选字段** `coactPairs?` / `coactSkipped?` |
| 字段是否可选 | — | ✅ **都是 `?`（可选）** |

**结论：✅ 不构成「半承诺」。** 三条理由：

1. **全部是 `type`-only 导出 ⇒ 运行时被擦除**（已实测：`dist/index.js` 0 命中）
   ⇒ 宿主**拿不到任何运行时对象**，**不存在行为承诺**。
2. `MergeEventPayload3c` **被生产代码实际使用** ⇒ 它是 P2 自己的事件契约，导出**完全正当**。
3. `CoactPair` / `CoactSkipped` 是 **`TouchEventPayload` 的字段类型**。
   `TouchEventPayload` **必须**导出（`touch()` 是阶段 1 的公开方法，它的**事件载荷**是 §8.4 的公开契约）
   ⇒ 导出**字段类型**是**机械必然**，不是「承诺 coacts 这个机制已存在」。
   再加上字段**可选**，宿主无法依赖它们出现。
   ⇒ 且 coacts **确实未实现**（锚定检查输出原文：「共激活边是阶段 3 的产物（P3-T01）⇒ 阶段 2 的
   `src/store/touch.ts` 里没有任何 `coacts` 代码」）。

**⚠️ Minor（文档）**：`src/index.ts` 文件头写「阶段 1 **只导这 10 个**…⇒ **只导这 10 个**：其余 13 个方法
分属阶段 2~5，在各自阶段落地前**不进导出面**」——这句话容易被读成「导出面只含阶段 1 的东西」，

### ③ 训练峰值内存 8.47GB

#### (a) 算缺陷还是优化项？

**⇒ 优化项（技术债），但严重级 **Major**；按设计的字面判据它「通过」。**

- **设计的判据是「下限」**：
  `DESIGN-v2.md:5942` 「**训练期资源门槛**：建库训练（100 万 × 768 维）**峰值内存 ≥ 3.5GB**…⇒
  **低配机器建库时要有心理预期**」；`DESIGN-v2.md:3613-3615` 同；
  `DEVELOPMENT-PLAN.md:1604-1605`「⚠️ **训练期峰值内存 ≥ 3.5GB**…这是本库**唯一**的高内存时刻」；
  `DEVELOPMENT-PLAN.md:2076`「训练期峰值内存 ≥ 3.5GB（**下限**，用于资源规划提醒）」。
  ⇒ **它不是「不许超过」的容量上限** ⇒ **8.47GB ≥ 3.5GB ⇒ 字面满足**。
- **但它仍然是个真问题**（三点）：
  1. **8.47GB 是「必要量」的 2.4 倍** ⇒ 在 8GB 机器上就是 OOM；
  2. 设计的**用途**恰恰是「让低配机器有心理预期」⇒ **如果 8.47GB 真是需求，那 3.5GB 这个
     资源规划数字本身是错的** ⇒ **必须回写设计**（§4.15.2/§4.15.3/§12 的 3.5GB 估算）；
  3. 根因**在生产代码里**，是**可定位、可量化、可修复**的实现缺陷。

#### 根因（QA 独立核实，与工程师的定位一致）

`src/vector/ivf.ts:102-118`：

```ts
export function readVectorMemories(db: Database.Database): VectorMemoryRow[] {
  const rows = db
    .prepare('SELECT id, embedding, deleted FROM memories WHERE embedding IS NOT NULL ORDER BY rowid')
    .all() as Array<{ id: string; embedding: Buffer; deleted: number }>;   // ← 一次性物化 100 万行
  const result: VectorMemoryRow[] = [];
  for (const row of rows) {
    result.push({ id: row.id, vector: blobToVector(row.embedding), … });   // ← 再分配 3.07GB Float32Array
  }
  return result;
}
```

⇒ `.all()` 的结果数组（id + 3KB BLOB ≈ **3.3GB**）与 `result` 里的 Float32Array（**3.07GB**）
**同时存活** ⇒ 峰值 ≈ **6.4GB**（+ Node/SQLite ⇒ 实测 **8.47GB**）。改流式可省约一半。

#### (b) 严重级 + 复现命令

- **严重级**：**Major**（资源/可用性缺陷，非功能错误）。
- **复现命令**：

  ```
  pnpm exec tsx bench/perf.ts --scale=1000000 --db=.tmp/bench/shared-1000000.db --reuse=true
  # 观察输出里的「峰值 RSS …MB」与落盘 JSON 的 phases.peakRssBytes（实测 8474386432 = 7.89 GiB）
  ```

  （灌库 + 训练在 100 万规模上约需 3~4 小时 ⇒ 复现成本高，建议用 20 万条的缩比版本做趋势验证。）

- ⚠️ **我没有改生产代码**（已核验 `src/vector/ivf.ts` 与 main **逐字节一致**，
  `git status --porcelain` 为空）。

#### ⚠️ 次级发现（Minor，但影响「这条软阈值到底测到了没有」）

落盘的 `docs/baseline/perf-1000000.json` 里：

```json
"phases": { "loadMs": …, "trainMs": …, "rssBeforeTrainBytes": 0,
            "peakRssBytes": 8474386432, "sampledPeakRssBytes": 0, … }
```

- `sampledPeakRssBytes: 0` ⇒ **「采样峰值」这个口径根本没采到数**；

### ④ 1 万条写入 P99 = 233.64ms 是冷启动离群值

#### (a) 已 committed 的 1 万条数据算「口径不一致的脏数据」吗？

**⇒ 不算（按工程师给的理由）；但它仍然是必须重刷的数据。**

**工程师给的理由不成立**，两条独立反证：

| # | 反证 | 证据 |
|---|---|---|
| 1 | 「`perf-10000.json` 生成于 22:14，**早于**『写入也预热 20 轮』的改动（22:29）」⇒ **不成立** | `git show fba3049:bench/perf.ts`（**就是加上该 JSON 的那个 commit**，22:18）的预热循环里**已经包含 `store.write({ content: warmContent, embedding: …, now })`** ⇒ 「写入也预热」**在产出该 JSON 的代码里已经存在**。`bench/perf.ts` 的历史只有 3 个 commit：`fba3049`(22:18) → `67b6bc3`(22:27) → `184920f`(22:30)，**预热里加写入在第一个 commit 就有了** |
| 2 | 「那个 233.64ms 的 max **就是第一次写入**」⇒ **不成立** | 同一份 JSON 里 `firstWriteMs: 4.5762`；而 `firstWriteMs` 的语义就是「**预热之后的第一次被计时的写入**」（`bench/perf.ts:230-241`：`if (index === 0) firstWriteMs = elapsed;`）⇒ **第一次写入是 4.58ms，不是 233.64ms** |
| 3 | 数据分布也不支持「首个样本」 | `writeLatency`：min 3.33 / p50 4.49 / p90 6.25 / p95 8.03 / **max 233.64** / count 50 ⇒ 是 **50 个样本里的 1 个离群点**，不是首个样本 |

⇒ **结论**：233.64ms 是一个**未被解释的单样本离群值**（GC / WAL checkpoint / 页缓存抖动均可能），
**不是**「第一次写入的一次性成本」。
⚠️ **我不确定的部分**：该离群值的**具体成因**无法从落盘物判定（JSON 只存分布，不存逐条样本与索引）
⇒ **不夸大结论**：我只断言「它不是第一次写入」，不断言「它一定是 GC」。

⇒ **但**：`docs/baseline/README.md:51` 写着「（实测 10k 规模：首次 245ms、后续 ~4ms）」
⇒ 这句话描述的是**未预热**的对照场景（它的上下文是「不预热 ⇒ P99 = max = 第一次写入」），
**与它所索引的那份 JSON（`firstWriteMs = 4.58`）对不上** ⇒ **README 与 JSON 口径不一致**
（README 描述的是一次没有落盘的对照测量）。

#### ⚠️ 口径再精确一层（与并行 QA 独立重算一致）：10k 的「不达标」是**离群值**，1M 的才是**真的**

| 规模 | 写入分布 | 解读 |
|---|---|---|
| **10k**（50 样本） | min 3.33 / **p50 4.49** / p90 6.25 / p95 8.03 / **p99 233.64** | ⚠️ **p50 只有 4.49ms**（达标）⇒ 「写入 P99 不达标」**完全由 1 个离群样本造成** ⇒ **不能据此判定「写入路径不达标」** |
| **1M**（50 样本） | min 14.9 / **p50 108.37** / p90 220.47 / p99 658.19 | 🔴 **p50 就 108ms（超标 20 倍）** ⇒ **真实规模效应**，不是离群值 |

⇒ ⇒ **「写入 P99 ≤ 5ms 在任何真实库上都不可能达标」这句话是过强的**（10k 的 p50 只有 4.49ms）
⇒ **正确表述**：「**在百万级规模上**，整体写入路径的 p50 就是 108ms ⇒ 远超 5ms 门槛」。

#### (b) 建议：**重刷三份 JSON**（不是「标注为过期」）

理由：

1. **这是结论问题，不是措辞问题**：该文件自己的 `failures` 写着
   「写入 P99 233.643ms > 5ms（样本 50、预热 20）」。
   若 233.64 是首写污染 ⇒ 重刷后大概率消失 ⇒ **结论会从「写入路径不达标」变成「达标」**
   ⇒ ⇒ **不重刷就不知道 P2 的写入门槛到底达不达标**。
2. **重刷时必须把样本数提上去**：`bench/lib/harness.ts:139-147` 的 `percentile()` 是 nearest-rank：
   `rank = ceil(0.99 × n)` ⇒ **n ≤ 50 时 P99 == max** ⇒
   **50 个样本的「P99」在统计上就是最大值，没有意义**。
   脚本默认是 `--queries=200 --writes=200`（`bench/perf.ts:329-330`），**基线却用的是 50**
   ⇒ ⇒ **重刷必须用 ≥200 的样本**（n=200 时 P99 取第 198 个，才是真正的 P99）。
3. ⚠️ **同一条问题也命中 1M 那份**：`perf-1000000.json` 的 `recallLatency.count = 10`
   ⇒ **P99 == max**；`writeLatency.count = 50` ⇒ **P99 == max**
   ⇒ ⇒ **两份基线的「P99」在统计上都是「最大值」** ⇒ **这直接削弱了 ⑥① 的结论**
   （连「超了 200ms」这个数本身都不该被当成 P99 看待，它只是「最差的一次」）。
4. ⇒ 建议：**三份 JSON 全部按 `--queries=200 --writes=200` 重刷**，并在重刷后：
   - 重新对照 `DEVELOPMENT-PLAN.md:2035-2038` 的四条硬门槛；
   - 若仍不达标 ⇒ **P2 的结论必须写成「性能门槛未达标，已知问题」**，而不是「P2 通过」。

**严重级**：**Major**（数据不可用于结论），**但不阻塞代码本身**。
