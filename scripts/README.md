# CI 契约门禁（阶段 0）

> 把 C25~C37 里**可机械检查**的部分做成脚本，让「文档与代码不一致」在 CI 里当场失败。
> 依据：DESIGN-v2.md §14.3.1（契约清单）/ §5 / §8.4 / §11.2 / §14.3.1 末的跨节锚定表；
> DEVELOPMENT-PLAN.md P0-T06、§7.2。

## ⚠️ 门禁怎么跑（先读这一段）

| 命令                                   | 是什么                                              | 是不是门禁 |
| -------------------------------------- | --------------------------------------------------- | ---------- |
| **`pnpm run verify`**                  | **门禁本体**：11 条子命令串成一条链                 | ✅ 是       |
| `pnpm run ci`                          | **别名**，内容恰好等于 `pnpm run verify`            | ✅ 是       |
| `pnpm ci` / `npm ci`（**不带 `run`**） | **包管理器的内建命令**（clean install）             | ❌ **不是** |

> ⚠️ **`pnpm ci` / `npm ci` 只做依赖安装，不做任何校验，退出码却是 0。**
> 那是 pnpm / npm 的**内建命令**（clean install），它会**遮蔽同名 script** ⇒
> 「跑了一下 `pnpm ci`，退出码 0」**不能**说明门禁跑过了。
> 这正是设计稿 C31 警告的症状：「一个从不失败的闸门，看起来在把关」。
>
> ⇒ **规范入口是 `pnpm run verify`**（`verify` 不是任何包管理器的内建命令名 ⇒ 不会被遮蔽）。
> ⇒ 这条纪律由 `scripts/check-gate-entry.ts` **机器可检**（见下表第 6 行）：
> 它断言 `scripts.ci` 的内容**恰好**是 `pnpm run verify`，
> 且 `scripts.verify` 串起的 11 条子命令**逐名**齐全、每一段都写成 `pnpm run <名>`。
> 有人把 `ci` 改回一串别的命令、或从 `verify` 上摘掉某条门禁 ⇒ 门禁当场失败。

⚠️ **它为什么值得存在**（**不是「再写一遍检查」**）：百万级基线有**三档采集**，
而「只属于某一档的数」与「跨档一致的数」在原文里长得很像 ⇒ ⇒ **靠眼力会漏**
（实测：曾把「文本路 87.9% / 向量 12.1%」写成「在两档里都不因 I/O 快慢而改变」，
而实测两档是 **12.1% vs 21.6%** ⇒ **靠人扫没抓住，靠脚本抓住了**）。

⚠️ **它自己也要守纪律**（§2.4 纪律 4 / 5 的自我约束）：
· **自证**：输出给**三个数**（扫了多少处 / 判了多少处 / 发现几处真缺）⇒ **数字变了它就该变**
  （实测：删掉一处档位限定 ⇒ `69 / 69 / 0` ⇒ `69 / 69 / 2` ⇒ 退出码 1 ⇒ **它有判别力，不是恒绿守卫**）；
· **幂等**：连跑两次输出**逐字相同** ⇒ **无随机性、无时间依赖**；
· **核对用「机制自己的读法」**：按**读者读 Markdown 的方式**四层定位
（本行 / 所在表的表头 / 上下文窗口 / 所属小节标题）⇒ **不是**「文件里出现过这个词就算」
⇒ ⇒ 这是 §2.4 纪律 5 ③ 的镜像：**「文件存在」≠「机制在用」**。

2. 在 `package.json` 的 `scripts` 里加 `check:xxx`，并串进 `ci`；
3. 在 `tests/contracts/` 写单测，**必须包含一个反例**（证明它真的能发现不一致）；
4. 在本 README 的对照表里登记。

## ⚠️ 提交前检查单（共享工作树 · 多 agent 并行）

> 下面是**真实踩过**的三条——不是预防性说教。每一条都对应一次「工作树是绿的、提交却不对」的事故。

### ① `git diff --cached --stat` —— 核对暂存区里**只有自己的文件**

共享工作树里，别人也在改文件。`git add -A` 会把**别人的在途改动**一起吞进你的 commit。

⇒ 只 `git add` **自己的那几个路径**，然后 `git diff --cached --stat` 确认清单。

### ② `git show HEAD:<file>` —— 核对关键实现**确实在提交里**

⚠️ **工作树绿 ≠ 提交绿**。下面的事故就发生在「跑完门禁全绿」之后、「提交」之前的几分钟里：

1. `git apply` 套用补丁 ⇒ `git status` 显示改动在位 ✅
2. 跑 `pnpm run verify` ⇒ **全绿** ✅（此刻补丁确实在位）
3. 跑 `pnpm build` ⇒ 通过 ✅
4. `git add` ⇒ ⚠️ **暂存区里只剩测试文件，实现没了**

原因：**另一个 agent 跑了一个 path-scoped 的 `git stash`（只含 `src/core/errors.ts`）**，
把我的实现从工作树里抽走了 ⇒ 若没核对，就会提交一个「**只有测试、没有实现**」的残缺 commit。

⇒ 提交后（或提交前 `git add` 之后）用 `git show HEAD:<关键文件> | grep '<关键符号>'` 确认它**在提交里**。

### ③ `git stash list` —— 瞄一眼有没有**静默**的 path-scoped stash

`git stash` / `git checkout -- <path>` / `git restore` 这类命令会**静默**抹掉别人的在途改动：
**不报错、不留痕迹**（不像 commit 有历史可查）。它只在「`git add` 之后核对暂存区」时才暴露。

⇒ 提交后顺手 `git stash list` 瞄一眼。
⚠️ **若发现某条 stash 的内容已被某个 commit 完全覆盖**（`git diff stash@{0} HEAD -- <file>` 为空），
它已**冗余**，且留着**有害**（将来有人 `git stash pop` 会把一份已提交的改动贴回去 ⇒ 制造冲突）⇒ **可以 drop**；
但 drop 前**必须**确认它里面**没有别人的未落地内容**。

### 附：门禁偶发「红」时的判定

⚠️ 某些受限环境下 vitest 解析配置时会写临时文件，可能被**拦截**（`EPERM`）⇒
vitest 报 `Unhandled Errors` 并**跳过部分测试文件**（表现为 `Test Files 7 passed` 而不是 8）。

⇒ **判定用语义判据，不要写死条数**：
「**收集数 == 仓库 `*.test.ts` 清单数**（按仓库清单求期望 ⇒ 外部常量，不是「本次跑出来几条」）
+ 全部 passed + **无** `Errors N errors` 行 + 退出码 0」。
⇒ 命中拦截时**重跑一次**；仍红才是真红。

⚠️ 这正是 C31 的纪律的**反向版**：把「本次实际跑出来几条」当期望值 ⇒ 条数一漂移就假绿/假红。
